# apps/api — testing reference

What the suites actually cover, spec by spec. It used to live in `apps/api/CLAUDE.md`;
the rules for running them stay there, this is the inventory.

> Related: [architecture](../architecture/api.md) · [apps/web testing](./web.md)

## Suites

- **Unit tests** (`pnpm test` / `pnpm test:watch` / `pnpm test:cov`): Jest config lives inline in `package.json` (`rootDir: "src"`, `testRegex: ".*\\.spec\\.ts$"` — matches `*.spec.ts` colocated with the code under `src`). `src/storage/storage.service.spec.ts` is the first real unit suite (exercises `save`/`createReadStream`/`exists`/`delete` against a temp directory, independent of Nest's DI or HTTP) — no unit tests exist yet for the `auth`/`users` CQRS handlers. `src/transcription/transcript-text.spec.ts` covers `extractTranscriptText`'s stripping of whisper.cpp's per-segment timestamp prefix, joining/whitespace collapsing across segments, and dropping any line that isn't a timestamped segment (a build/log line interleaved with real segments, or the whole input having none). `src/transcription/transcription.service.spec.ts` covers `TranscriptionService.transcribe` against a stubbed `WHISPER_RUNNER`, both the success path (raw whisper output piped through `extractTranscriptText`) and the runner rejecting. `src/meetings/commands/handlers/upload-recording.handler.spec.ts` covers `UploadRecordingHandler`: that `RecordingsRepository.create` (a plain insert, not an upsert) persists the new row as `UPLOADED` and the handler responds without waiting on transcription; that `StorageService.pruneMeetingDir` is called with the full current set of the meeting's recordings' `storagePath`s (via a stubbed `findByMeetingId`), not just the one just uploaded; the background transcription status transition `UPLOADED` → `PROCESSING` → `READY` (with `transcriptText`) on a successful stubbed transcription, → `FAILED` on a rejected one; and that `updateStatusIfCurrent`'s staleness guard is respected (a write matched by `recordingId` alone that no longer finds the row — because it's since been deleted — short-circuits the rest of the background run). Run a single unit test file: `pnpm test -- <name>.spec.ts` (Jest pattern match); a single test case: `pnpm test -- -t "test name"`.
- **E2e tests** (`pnpm test:e2e`): separate config at `test/jest-e2e.json` (matches `*.e2e-spec.ts` under `test/`). Requires `docker compose up -d postgres` running first — `test/auth.e2e-spec.ts`, `test/users-profile.e2e-spec.ts`, `test/meetings.e2e-spec.ts`, `test/meetings-recording.e2e-spec.ts` and `test/users-avatar.e2e-spec.ts` boot the real `AppModule` and hit the actual Postgres database from `docker-compose.yml` (via Prisma), truncating their tables (`users`; `users`; `meetings`+`users`; `meetingRecording`+`meetings`+`users`; `users`) in a `beforeEach` for isolation. `users-profile.e2e-spec.ts` covers `GET /users/me`/`PATCH /users/me`: own-profile fields, name trimming/blank-to-null, explicit `name: null` clearing an already-set name, an omitted `name` leaving it untouched, the 100-char validation error, auth rejection, and cross-user isolation (one user's request never reads/writes another's row); it also covers `POST /users/me/password`: a correct `currentPassword` returns a new `accessToken` that authenticates `GET /users/me` and that `POST /auth/login` accepts as the new password (and rejects as the old one), a wrong `currentPassword` and a `newPassword` equal to the current one both 400 while leaving the stored hash unchanged (`POST /auth/login` with the original password still succeeds), and an unauthenticated request 401s. Because multiple e2e spec files share and truncate the same real database, `test/jest-e2e.json` sets `"maxWorkers": 1` so suites run serially; without it, Jest's default parallel workers can interleave one file's `deleteMany()` with another file's in-flight test and cause spurious foreign-key errors. `meetings-recording.e2e-spec.ts` additionally points `UPLOADS_DIR` at a dedicated temp directory (set in `beforeAll`, before any test compiles the `AppModule`, since `dotenv` never overwrites an already-set env var) so it doesn't write real recording files into the repo, and wipes that directory in `afterAll`; its 413 (size-limit) case builds its own one-off app with a temporarily tiny `MAX_UPLOAD_SIZE_BYTES` rather than reusing the shared `app`. It stubs `WHISPER_RUNNER` with a never-resolving promise (`AppModule`'s `TestingModule` overrides the provider) so background transcription never races or flakes against a real Whisper install. Covers `POST /meetings/:id/recordings`: an mp4/mp3 upload (201, `UPLOADED` row, `transcriptText` null), adding a second file alongside the first as two independent rows with both files on disk (not a replace), path-traversal/auth/ownership/415/413/malformed-body rejections writing nothing to disk. `DELETE /meetings/:id/recordings/:recordingId`: deleting one recording (204, file and row gone) while a sibling recording's file/row/streamability are left fully intact; deleting a `READY`-with-transcript recording removes the row (and its transcript) entirely, with a fresh re-upload afterward starting clean again; 404 for a repeat delete, an out-of-band-deleted row (Prisma's `P2025` translated to 404, not a 500), a foreign meeting, or a `recordingId` belonging to a different meeting. `GET /meetings/:id/recordings/:recordingId/content`: full-file checksum match, each of two recordings on the same meeting streaming independently by its own `recordingId` (including their distinct `Content-Type`s), `Range` → 206 with the correct `Content-Range`/`Content-Length`, the `?token=` query-param auth fallback (and its rejection on a route not marked `@AllowQueryToken()`), 404s for a missing/foreign/cross-meeting recording. The `recordings`/`recordingCount` fields on both read routes (`GET /meetings/:id` returns `recordings: []` for a fresh meeting, then every uploaded file with independent `status`/`transcriptText`; `GET /meetings` returns each meeting's `recordingCount` matching how many files were uploaded to it). Cascade delete of every `meeting_recordings` row for a meeting on both `prisma.meeting.delete` and `prisma.user.delete` (there is no HTTP route for either, so those two cases call Prisma directly). `users-avatar.e2e-spec.ts` mirrors `meetings-recording.e2e-spec.ts`'s pattern for `POST`/`DELETE /users/me/avatar`: points `UPLOADS_DIR` at its own dedicated temp directory in `beforeAll`/wipes it in `afterAll`, its 413 case builds a one-off app with a temporarily tiny `MAX_AVATAR_SIZE_BYTES`, and it covers a PNG/JPEG/WebP upload (201 with metadata and a file under `{UPLOADS_DIR}/avatars/{userId}/`), a second upload replacing the first (one row, only the new file on disk), a disallowed extension/MIME type (415, nothing written), an oversized file (413, nothing written), delete (204, file gone) and a repeat delete (404), and 401 without a token on both routes. Run a single e2e file: `pnpm test:e2e -- auth.e2e-spec.ts`; a single test case: `pnpm test:e2e -- -t "test name"`.
- **`test/find-tasks-mcp.e2e-spec.ts`** boots the real `AppModule` (for `/auth/register` and `POST /meetings`, to get a real JWT and a real meeting) and, per test, spawns the actual `src/mcp/find-tasks-server.ts` as a real subprocess (`ts-node/register/transpile-only`, no build step needed) and drives it with a real `@modelcontextprotocol/sdk` `Client` over stdio — nothing here is mocked, this is the same standalone process/protocol an external MCP client would use. Covers: `find_tasks` returning a task seeded directly via `prisma.task.create` when the caller's own `MCP_ACCESS_TOKEN` and the task's `sourceMeetingId` agree; the same call returning `isError: true` (not the task) when the token belongs to a different user than the meeting's owner; and an invalid `MCP_ACCESS_TOKEN` failing before any tool call can succeed at all, since the server verifies it once at startup and never attaches the transport otherwise. Also covers `upsert_task`: creating a new `Task` (verified both via the tool's own reply and a direct `prisma.task.findUnique` lookup, so the write is confirmed to have actually gone through `TaskService`, not just returned a plausible-looking reply), updating the one existing similar task in the same meeting instead of creating a duplicate (asserting `prisma.task.count()` stays at 1), and refusing to write into a meeting owned by a different user (`isError: true`, `prisma.task.count()` stays at 0). Also covers the `gather_meeting_info` prompt: `client.listPrompts()` includes it; `client.getPrompt({ name: 'gather_meeting_info', arguments: { meetingId } })` for the caller's own meeting returns one `user`-role text message containing the meeting's title, its participants (joined, asserted against a meeting created with two real email addresses), and the `meetingId` itself; and the same call for a meeting owned by a different user rejects the promise outright (a prompt has no `isError` field to check — an ownership failure surfaces as a thrown JSON-RPC error instead, unlike the two tools above).
- Both suites currently cover `auth` and `meetings` behavior only through the e2e layer (HTTP-level, real DB) — there is no unit-level coverage of individual CQRS handlers (e.g. `RegisterUserHandler`, `LoginUserHandler`, `CreateUserHandler`) in isolation.

## Lint

ESLint (`eslint.config.mjs`) uses `typescript-eslint` recommendedTypeChecked + `eslint-plugin-prettier`; notably `@typescript-eslint/no-explicit-any` is off, and `no-floating-promises` / `no-unsafe-argument` are warnings, not errors.
