# apps/web — architecture reference

`apps/web/CLAUDE.md` keeps the rules and the boundaries.

## Pages, components and libraries

Next.js App Router app, wired up with Tailwind CSS v4 and HeroUI v3. No longer the default `create-next-app` scaffold content — `page.tsx`/`layout.tsx` were replaced with a minimal client-side-authenticated app shell:

- `src/app/layout.tsx` — root layout; `body` carries HeroUI's semantic `bg-background text-foreground` classes; page `metadata` (title/description) set for this app rather than the `create-next-app` defaults
- `src/app/page.tsx` — home page (`/`), a client component (`'use client'`). Auth is handled by `useAuthenticatedUser()` (`src/lib/useAuthenticatedUser.ts`): while `user` is `null` (no valid stored session, or the check hasn't resolved yet) it shows a HeroUI `Spinner` and, if there's really no session, redirects to `/login`. Once `user` is set, an effect fetches `getMeetings()` (`src/lib/api.ts`, `GET /meetings`, returning `MeetingListItem[]` — `Meeting` plus `hasRecording`) and the page renders `AppHeader` (welcoming the user by email, with a sign-out button wired to the hook's `signOut`) followed by: a "Recent meetings" `Card` listing `MeetingRow`s for the 3 most recently dated meetings (client-side sort/slice — the API returns the full unsorted list, no `limit`/`sort` params exist), shown only when there is at least one meeting, and an "All meetings" `Card` listing every meeting as a `MeetingRow` with a `Total: N` count. An inline error (from `ApiError`) renders if the meetings fetch fails. Both lists pass `onUploaded` (a callback that flips a meeting's `hasRecording` to `true` in local state by id) down to `MeetingRow`, so a meeting appearing in both lists stays in sync after an upload from either one, without a refetch.
- `src/app/meetings/[id]/page.tsx` — meeting detail page (`/meetings/{id}`), a client component reading the id via `useParams()`. Same `useAuthenticatedUser()` pattern as `page.tsx`; once authed, an effect fetches `getMeeting(id)` (`GET /meetings/:id`, returning `MeetingDetail` — `Meeting` plus `recording: Recording | null`) and renders the meeting's title/date/participants plus a "Recording" `Card` whose content toggles between `RecordingCard` (when `meeting.recording` exists and the user isn't mid-replace) and `RecordingUploader` (otherwise). `isReplacing` local state drives the "Replace" flow: `RecordingCard`'s `onReplace` sets it, swapping in `RecordingUploader`; a successful upload (`onUploaded`) clears it and updates `meeting.recording` in local state directly, no refetch. While the recording's `status` is `UPLOADED` or `PROCESSING`, a second effect polls `getMeeting(id)` every 4 seconds (cleared once status settles or on unmount) so the page catches up with the API's background transcription without a manual reload; a `pollGenerationRef` counter, bumped by the direct-update path above, invalidates a poll response that resolves after a more recent local update, and a poll failure stops the interval and surfaces the same inline error as the initial load. A 404 `ApiError` (unknown or another user's meeting) renders as an inline "Meeting not found" message rather than a blank page.
- `src/app/login/page.tsx` — `/login`, a client component mirroring `register/page.tsx`'s `Card`/`Form` structure (email + password, show/hide toggle) but posting to `POST /auth/login` via `loginUser` (`src/lib/api.ts`). On success it stores the returned `accessToken` and redirects to `/`; on failure (e.g. wrong credentials → 401, same message regardless of which field was wrong) it renders the API's error message inline. Footer links to `/register` for new users.
- `src/app/register/page.tsx` — `/register`, a client component rendering a HeroUI `Card`/`Form` that posts an email/password to `POST /auth/register` via `registerUser` from `src/lib/api.ts`. On success it stores the returned `accessToken` (`storeAccessToken`, `src/lib/auth.ts`) and redirects to `/`; on failure (e.g. duplicate email → 409) it renders the API's error message inline. Client-side validation distinguishes "email is required" from "invalid email format", enforces an 8-character password minimum, and the password field has a show/hide toggle; controls are sized to the 44px (mobile) / 40px (desktop) touch-target minimum. Footer links to `/login` for existing users.
- `src/components/` — one component per file, grouped into subfolders by kind rather than kept flat:
  - `components/layout/AppHeader.tsx` — shared header rendered at the top of every page (`login`, `register`, `page.tsx`): app logo/name (as the page's `h1`) on the left; on the right, when `email` is passed, a `UserAvatar` plus the display name (falling back to `email`) wrapped in a HeroUI `Link` to `/profile`, and a "Sign out" button when `onSignOut` is passed (home page only — `login`/`register` render it with no props, logo/name only).
  - `components/meetings/MeetingRow.tsx` — a single meeting's card row (title, calendar-icon-prefixed formatted date, users-icon-prefixed comma-joined participant list), used by `page.tsx` for both the "Recent" and "All meetings" lists; takes an optional `highlighted` prop for the blue-tinted "Recent meetings" styling. The title/date/participants sit inside a plain `<button>` (not a HeroUI `Button`, so it composes cleanly with block content) whose `onClick` does `router.push('/meetings/{id}')`; below it, a separate row shows either a "Recording" `Chip` (when `hasRecording`) or an "Upload" `Button` that opens `UploadRecordingModal` — kept as a sibling rather than nested inside the navigation button so clicking it can't also trigger navigation, with no `stopPropagation` needed.
  - `components/meetings/UploadRecordingModal.tsx` — a HeroUI `Modal.Backdrop` (controlled via `isOpen`/`onOpenChange` props, no `<Modal>` trigger wrapper) around `RecordingUploader`, used by `MeetingRow` for uploading without leaving the list.
  - `components/meetings/RecordingUploader.tsx` — the upload area: a dashed drop zone with a hidden `<input type="file">` triggered by a "Choose file" button, plus native drag-and-drop handlers. Validates MIME type and size client-side (`ALLOWED_MIME_TYPES`/`MAX_SIZE_BYTES` constants — mirror, and must be kept in sync with, `apps/api/.env`'s `ALLOWED_RECORDING_MIME_TYPES`/`MAX_UPLOAD_SIZE_BYTES`) before calling `uploadMeetingRecording`; shows a HeroUI `ProgressBar` during upload with a "Cancel" button that aborts via `AbortController`, and an inline error message (from `ApiError`, or the client-side validation message) otherwise. The drop zone, file input and drag-over handling all no-op while `isUploading` is true, so a second file dropped mid-upload can't hijack `abortControllerRef` out from under the first one's in-flight request. Used by both `/meetings/[id]/page.tsx` (inline) and `UploadRecordingModal` (inside a modal).
  - `components/meetings/RecordingCard.tsx` — the existing-recording block: an `<audio controls>` player for an `audio/mpeg` recording or a `<video controls>` player for the other (video) MIME types (`src` from `getRecordingContentUrl` either way), filename/human-readable size/upload date, a `RecordingStatusChip`, a transcript block shown only when `status === 'READY'` (`recording.transcriptText`, scrollable, whitespace preserved) or a failure notice shown only when `status === 'FAILED'`, and "Replace" (calls `onReplace`, a parent-supplied callback — no API call here) / "Delete" (opens a HeroUI `Modal.Backdrop` confirmation, not `window.confirm`, then calls `deleteMeetingRecording` and `onDeleted`) buttons.
  - `components/meetings/RecordingStatusChip.tsx` — maps a `RecordingStatus` (`UPLOADED`/`PROCESSING`/`READY`/`FAILED`) to a colored HeroUI `Chip` (`accent`/`warning`/`success`/`danger`); used by `RecordingCard`.
  - `components/icons/` — one small inline SVG icon component per file (`EyeIcon.tsx`/`EyeOffIcon.tsx` for password visibility toggles, `VideoCameraIcon.tsx` for the app logo and the recording badge, `CalendarIcon.tsx`/`UsersIcon.tsx` for meeting metadata, `UploadIcon.tsx`/`TrashIcon.tsx`/`XMarkIcon.tsx` for recording actions), re-exported through `icons/index.ts` so call sites import from `@/components/icons` rather than each file individually.
- `src/lib/api.ts` — thin `fetch` wrapper for calling `apps/api`: reads the base URL from `NEXT_PUBLIC_API_URL` (env var, see below), exposes `registerUser`, `loginUser`, `getMeetings`, `getMeeting`, `deleteMeetingRecording` and `getRecordingContentUrl` (all attaching `Authorization: Bearer <token>` via `getAccessToken()` from `src/lib/auth.ts`, except `getRecordingContentUrl` which appends the token as a `?token=` query param instead, since a `<video>` element's `src` can't set request headers and the API's `JwtAuthGuard` accepts either form), and throws `ApiError` (with the HTTP status and the API's `message`) on non-2xx responses. The shared `handleResponse` returns `undefined` for a 204 (no body to parse) rather than always calling `response.json()`, so `deleteMeetingRecording` can reuse it like every other function here instead of hand-rolling its own error handling. `uploadMeetingRecording` is the one exception to the shared `fetch`-based `handleResponse` plumbing: it's built on `XMLHttpRequest` because `fetch` exposes no upload-progress events, taking an `{ onProgress, signal }` options object (an `AbortSignal` cancels the in-flight `XMLHttpRequest`, rejecting with `UploadCancelledError` rather than `ApiError` so callers can distinguish a user-initiated cancel from a real failure) and reusing the same error-message extraction as the rest of the file.
- `src/lib/auth.ts` — client-side-only auth state, backed by `localStorage` (key `accessToken`, no cookie/session — nothing server-side reads it yet, so there's no SSR/middleware auth gate, only the client-side check via `useAuthenticatedUser`). `storeAccessToken`/`clearAccessToken` write/clear the token, `getAccessToken()` reads the raw token (used by `src/lib/api.ts` to authenticate requests); `getStoredUser()` decodes the JWT's payload (base64, no signature verification — the API is the source of truth) and returns `{ email }`, or `null` if missing/expired (`exp` claim), self-clearing the stored token when expired.
- `src/lib/useAuthenticatedUser.ts` — `useAuthenticatedUser()`, the shared client-side auth guard for every page that requires a signed-in user (`page.tsx`, `meetings/[id]/page.tsx`): on mount, redirects to `/login` if `getStoredUser()` finds nothing valid, otherwise exposes `{ user, signOut }`; `user` stays `null` until the check resolves, which callers use as their own loading state. Extracted once two pages needed the identical redirect-then-render-a-spinner-until-authed pattern, so a third page doesn't have to copy it again.
- `src/lib/format.ts` — `formatDateTime()`, the single `Intl.DateTimeFormat('en-US', { dateStyle: 'medium', timeStyle: 'short' })` used everywhere a meeting or recording timestamp is displayed (`MeetingRow`, `RecordingCard`, `meetings/[id]/page.tsx`).
- `src/app/globals.css` — global styles. Starts with `@import 'tailwindcss';` then `@import '@heroui/styles';` (order matters); the old hand-rolled `--background`/`--foreground` light/dark vars were removed in favor of HeroUI's own theme variables (see below)
- `postcss.config.mjs` — registers the `@tailwindcss/postcss` plugin, required for Tailwind v4

## Calling apps/api

`NEXT_PUBLIC_API_URL` (see `.env.example`, defaults to `http://localhost:3001` in `src/lib/api.ts` if unset) is the base URL `src/lib/api.ts` calls. It must be prefixed `NEXT_PUBLIC_` to be readable in client components (Next.js only inlines env vars with that prefix into the browser bundle). It must point at `apps/api`'s port (`PORT` in `apps/api/.env`, default `3001`).

## HeroUI v3

- Packages: `@heroui/react`, `@heroui/styles`, `tailwind-variants`, plus `tailwindcss`/`@tailwindcss/postcss`/`postcss` for the Tailwind v4 base it builds on.
- No provider component is needed (unlike HeroUI v2's `HeroUIProvider`).
- Components use compound composition (e.g. `Card.Header`) and `onPress` instead of `onClick`; import from `@heroui/react`.
- Theming is CSS-variable/`oklch`-based via `@heroui/styles`, switching on `[data-theme='dark']`/`[data-theme='light']` rather than `prefers-color-scheme`. No theme switcher is wired up yet — the app currently renders HeroUI's default light theme (`:root`'s values apply with no `data-theme` attribute set), except `src/app/globals.css` darkens HeroUI's default `--accent`/`--muted` tokens to meet WCAG AA contrast (4.5:1) — HeroUI's originals fell short for button text on `--accent` and placeholder text on `--muted`.
