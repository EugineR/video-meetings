# apps/web — architecture reference

The per-file inventory of the Next.js frontend. It used to live in `apps/web/CLAUDE.md`,
where every session loaded all 13 KB of it before doing anything. Read the part you need;
`apps/web/CLAUDE.md` keeps the rules and the boundaries.

> Related: [testing](../testing/web.md) · [apps/api architecture](./api.md)

## Pages, components and libraries

Next.js App Router app, wired up with Tailwind CSS v4, HeroUI v3 and TanStack Query (`@tanstack/react-query`) for the server-state cache. No longer the default `create-next-app` scaffold content — `page.tsx`/`layout.tsx` were replaced with a minimal client-side-authenticated app shell:

- `src/app/layout.tsx` — root layout; `body` carries HeroUI's semantic `bg-background text-foreground` classes and wraps `{children}` in `QueryProvider` (both route groups share one query cache — signing in has to be able to clear what the previous session left behind); page `metadata` (title/description) set for this app rather than the `create-next-app` defaults
- `src/app/(app)/layout.tsx` — layout of the authenticated route group: `AuthenticatedUserProvider` only (the one auth guard and the one place `useAuthenticatedUser()` is called — see `components/layout/` below). It contributes no visual chrome; that is owned one level down, by whichever child route group a page falls into.
- `src/app/(app)/(dashboard)/layout.tsx` — layout of `/`, the Meetwise dashboard redesign: `DashboardShell` (sidebar/top-bar chrome, see `components/layout/` below).
- `src/app/(app)/(dashboard)/error.tsx` — that group's error boundary, rendering `AppErrorState` (see `components/layout/` below) — kept one level below `(app)/error.tsx` so `DashboardShell` stays mounted during the error rather than being replaced along with it.
- `src/app/(app)/(workspace)/layout.tsx` — layout of `/meetings/[id]`, `/profile`, `/profile/edit`: `AppShell` (background gradient, `AppHeader`, the centered `max-w-2xl` content container), unchanged by the dashboard redesign. Every page in the group renders content only: no shell, no header, no `!user` spinner of its own, and the header is identical across all three routes — including `/meetings/{id}`, which used to pass only `email` to its own `AppHeader` and so lost the avatar.
- `src/app/(app)/(workspace)/error.tsx` — that group's error boundary, rendering `AppErrorState`, same reasoning as `(dashboard)/error.tsx` above.
- `src/app/(app)/error.tsx` — fallback error boundary for an error thrown by `(app)/layout.tsx` itself (the auth guard); renders `AppErrorState` too. Splitting the shell into two child route groups moved the everyday case (an error inside a page) to their own boundaries — a route group's `error.tsx` only catches errors in its children, not in its own `layout.tsx`, so a single `(app)/error.tsx` would have unmounted `DashboardShell`/`AppShell` along with the page once they became separate layouts.
- `src/app/(auth)/layout.tsx` — layout of the unauthenticated group (`/login`, `/register`): `AuthShell` — the same background, the brand-only `BrandHeader` (no user slot, no sign-out), and the centered `max-w-md` slot each page renders its `Card` into.
- `src/app/(app)/(dashboard)/page.tsx` — home page (`/`), a client component (`'use client'`). Auth and the sidebar/top-bar chrome come from the group layout above; `useAuthenticatedUserContext()` and `useProfileQuery()` supply the time-of-day greeting (`getGreeting()`, `src/lib/format.ts`) and display name. `useMeetingsQuery()` (`src/lib/queries/meetings.ts`, `GET /meetings` via `getMeetings()`, returning `MeetingListItem[]` — `Meeting` plus `recordingCount`) supplies the list; a "+ Create meeting" `Button` (`PlusIcon`) opens `CreateMeetingModal`; a "Recent meetings" section renders `RecentMeetingCard`s for the 3 most recently dated meetings (`recentMeetings()`, client-side sort/slice — the API returns the full unsorted list), shown only when there is at least one meeting; an "All meetings" section renders every meeting as `MeetingTableRow` (desktop, `hidden lg:block`) or `MeetingListRow` (mobile, `lg:hidden`) inside one shared bordered container, with an inert Filter control next to the heading (see below). An inline error (from `ApiError`) renders if the meetings fetch fails — as a line above the list, not in place of it, same reasoning as before the redesign. All three row/card components give an `onUploaded` that calls `useCountUploadedRecording()` with that row's meeting id, and `useAddCreatedMeeting()` is `CreateMeetingModal`'s `onCreated` — both unchanged from the pre-redesign page. The page itself holds no server state and runs no fetching effect; its only `useState` is the create-modal's open flag.

  The design's mockup shows several controls this app has no feature behind yet — a search field and notification bell (`AppTopBar`/`MobileTopBar`), a "View all" link with no target, a Filter control, `AppSidebar`/`MobileBottomNav`/`MobileNavDrawer`'s "Overview"/"Tasks"/"People" nav items, and a storage-usage card (`SidebarStorageUsage`). All of these are markup only, wired to nothing, meant to be feature-flagged once the feature exists. Two exceptions, where the mockup's only visible trigger for something that already works is an overflow "…" control: `SidebarUserProfile`'s account menu (`Dropdown`, HeroUI) has one real item, "Sign out" (the existing `onSignOut`); `MeetingTableRow`/`MeetingListRow`'s actions menu has one real item, "Upload recording" (shown only while `recordingCount === 0`), opening the existing `UploadRecordingModal`. Two further mockup details have no backing data and were substituted with real data instead of fabricated: the recent-card's description slot shows the meeting's participants (no `description` field exists on `Meeting`), and its Status badge/the table's Status column reduce to two states `recordingCount` can actually support ("Uploaded" / "Needs upload") rather than the mockup's per-recording-status states.

- `src/app/(app)/(workspace)/meetings/[id]/page.tsx` — meeting detail page (`/meetings/{id}`), a client component reading the id via `useParams()`. Auth, shell and header come from `(workspace)/layout.tsx`; a single `useMeetingDetailQuery(id)` call (`src/lib/queries/meetings.ts`, `GET /meetings/:id` via `getMeeting`, returning `MeetingDetail` — `Meeting` plus `recordings: Recording[]` and `summary`) supplies everything the page renders — `meeting`, `meetingError`, `isSummaryPending`, `showSummarySection` and the two recording callbacks — so the page is JSX plus that one hook: no fetching effect, no polling interval, no reconciliation state of its own. It renders a `Button` (`variant="secondary"`, `ArrowLeftIcon`) that calls `router.back()`, the meeting's title/date/participants, and a "Recordings" `Card` starting with an always-present `RecordingUploader` (height-capped to 256px so it never grows past the 200–300px range regardless of state), pinned above every `meeting.recordings` entry rendered as a compact `RecordingCard` tile — there is no toggle between a single card and the uploader, so a user can keep adding files. `onRecordingUploaded` (handed to `RecordingUploader`) and `onRecordingDeleted` (handed to every `RecordingCard`) each add or drop that one recording in the cached meeting and then invalidate its query entry, so the tile list reacts to the click at once while the transcript and the summary still come from the API rather than from a hand-patched copy. `isSummaryPending` is passed to `MeetingSummarySection` as `isUpdating`. A 404 `ApiError` (unknown or another user's meeting) renders as an inline "Meeting not found" message rather than a blank page.
- `src/app/(app)/(workspace)/profile/page.tsx` — `/profile`, the read-only account page: `useProfileQuery()` supplies `{ profile, profileError }` (the same cache entry the header observes, so arriving from any authenticated route renders from cache without a request), rendering a `Card` with the `size="profile"` `UserAvatar`, the display name (or the email when unset), the email, the `formatDateTime`-formatted registration date behind a `CalendarIcon`, and a "Edit profile" `Button` routing to `/profile/edit`. A failed fetch renders as an `ErrorText` inside the card, a pending one as `LoadingState subject="profile"`; neither the shell nor the `!user` guard is this page's concern.
- `src/app/(app)/(workspace)/profile/edit/page.tsx` — `/profile/edit`, the editing page: the same `useProfileQuery()` read, plus the one `handleSaved` that applies the shared `ProfileSaved` payload the three sections hand back — a `profile` delta to `useApplyProfile()` (a `setQueryData` merge, no refetch) and a reissued `accessToken` to `applyAccessToken` from `useAuthenticatedUserContext()`. It renders `AvatarSection`, `DisplayNameSection` and `PasswordSection` (each independently submittable, each in its own `Card`) below a heading row with a "Back to profile" `Button`. The page holds no state of its own: the sections own their form state, the query layer owns the profile.
- `src/app/(auth)/login/page.tsx` — `/login`, a client component mirroring `register/page.tsx`'s `Card`/`Form` structure (a `TextInputField` for the email and a `PasswordField` for the password) but posting to `POST /auth/login` via `loginUser` (`src/lib/api.ts`). On success it stores the returned `accessToken`, resets the query cache (`useResetQueryCache()` — a new session starts here) and redirects to `/`; on failure it renders the API's error message on the form-level `ErrorText` via `toFormErrorState`, with no status→field map on purpose: wrong credentials come back as one 401 with one message regardless of which of the two fields was wrong, so pinning it to a field would be a guess. Editing either field clears that message, as on every other form here; the email's `validate` is the shared `validateEmail`. Footer links to `/register` for new users.
- `src/app/(auth)/register/page.tsx` — `/register`, a client component rendering a HeroUI `Card`/`Form` that posts an email/password to `POST /auth/register` via `registerUser` from `src/lib/api.ts`. On success it stores the returned `accessToken` (`storeAccessToken`, `src/lib/auth.ts`), resets the query cache (`useResetQueryCache()`) and redirects to `/`; on failure `toFormErrorState` routes a 409 (`Email is already registered` — the one status this endpoint answers that is unambiguously about one field) onto the email field and anything else onto the form-level `ErrorText`; editing either field clears that state again, which on the field-level 409 also releases the `customError` HeroUI's native validation put on the input. Client-side validation is `validateEmail` and `validatePasswordLength` from `src/lib/validation.ts`, not rules written out here; the email is a `TextInputField`, the password a `PasswordField` with its show/hide toggle, both sized to the 44px (mobile) / 40px (desktop) touch-target minimum by the primitive rather than by this page. Footer links to `/login` for existing users.
- `src/components/` — one component per file, grouped into subfolders by kind rather than kept flat. `components/ui/` is the shared, feature-agnostic layer: nothing in it knows about meetings or profiles, and it — together with `components/icons/`, which knows even less — is what `components/layout/`, `components/meetings/` and `components/profile/` may reach into. The seal is between those last three, and each direction of it is a `no-restricted-imports` rule in `eslint.config.mjs` (see [Lint](#lint)): `meetings/` and `profile/` cannot import each other, `layout/` cannot import either, and `ui/` cannot import any of the three.
  - `components/ui/Button.tsx` — HeroUI's `Button` re-exported with the app's touch target already applied: it runs `touchTarget()` (`src/lib/touchTarget.ts`) over its `className`, defaulting the shape to `square` for an `isIconOnly` button and `height` for every other, with a `touchTarget` prop for the two cases that default cannot see (`block` for a multi-line label, `inset` for a button filling a container that is already one target tall). Every button in `src/` — 17 files — imports this instead of `@heroui/react`, because the height used to be a `className="h-11 md:h-10"` an author had to remember, and the buttons that forgot it — both modal footers, both profile Save buttons, the password eye toggle — rendered at HeroUI's default 40px/36px and missed the minimum. `size` still means HeroUI's text/padding scale, it just no longer decides the height. `className` is merged last, so a call site can still restyle everything but the target.
  - `components/ui/ErrorText.tsx` — the app's one inline error line: `<p className="text-sm text-danger" role="alert">{children}</p>`, and the only file in `src/` carrying that class string. Deliberately prop-less beyond `children` (no `className` escape hatch) so every failure — a form-level API error, a failed fetch, a rejected file, a failed transcription or summarization — reads and announces identically. Used by both auth pages, all four `(app)` pages, `(app)/error.tsx`, `ConfirmModal` (its `error` slot), `CreateMeetingModal`, `MeetingSummarySection`, `RecordingCard`, `RecordingUploader`, `AvatarSection`, `DisplayNameSection` and `PasswordSection` — 15 files, which is every place the app reports a failure. `eslint.config.mjs` fails the lint run on the raw class string anywhere else under `src/`.
  - `components/ui/SuccessText.tsx` — the same line in `text-success` with `role="status"` rather than `role="alert"`: a "Display name saved."/"Password changed." confirmation is polite (the screen reader finishes its sentence first), an error interrupts. Used by `DisplayNameSection` and `PasswordSection`.
  - `components/ui/LoadingState.tsx` — the centered spinner block, with one padding and one label form for the whole app. `variant="section"` (default) is the in-page block (`flex justify-center py-12`) used by `page.tsx`, `meetings/[id]/page.tsx`, `profile/page.tsx` and `profile/edit/page.tsx`; `variant="page"` (`flex min-h-screen items-center justify-center`) is the authenticated group's guard screen in `AuthenticatedUserProvider`, which renders before any layout chrome exists. The optional `subject` prop labels the spinner `Loading {subject}` (`"meetings"`, `"meeting"`, `"profile"`), and omitting it gives the bare `Loading` the guard uses. Before it existed the same block was written out with three paddings (`py-4`, `py-12`, full-screen), two spinner sizes and three unrelated `aria-label` values.
  - `components/ui/TextInputField.tsx` — the app's one single-line text field: HeroUI `TextField` wrapping `Label` + `Input` (`variant="secondary"`, sized by `touchTarget()` from `src/lib/touchTarget.ts` rather than by a height written out here) + an optional `Description` + `FieldError`. Controlled (`value`/`onChange`) with an optional `validate` returning the message for an invalid value, and prop-less beyond that — no `className` — so no call site can drift off the shared touch target or treatment. `type` sits on the `Input` rather than on `TextField` because `TextField` types only text-like inputs and the create-meeting date field is a `datetime-local`. Used by `/login`, `/register`, `CreateMeetingModal` (title, date, participants) and `DisplayNameSection`.
  - `components/ui/PasswordField.tsx` — the same anatomy for a password, plus the show/hide eye toggle (`EyeIcon`/`EyeOffIcon` in an `InputGroup.Suffix`) that used to be hand-written four times over. The `InputGroup` takes `touchTarget()` and the toggle inside it `touchTarget="inset"`, so the toggle fills the group's content box exactly instead of being pinned to 44px and overflowing it. Visibility is local state — which field is revealed concerns nobody else — and the toggle's `aria-label` is derived from `label` (`"New password"` → `"Show new password"`) rather than passed in, so the five call sites cannot end up with five wordings the way they had. Used by `/login`, `/register` and all three inputs in `PasswordSection`.
  - `components/ui/ConfirmModal.tsx` — the app's one "are you sure?" dialog, for destructive actions only: `heading`, the consequence as `children`, a `confirmLabel` on a fixed `variant="danger"` button, `isPending` while the action runs, and an `error` slot rendered **inside** `Modal.Body`. Cancel is HeroUI's `slot="close"`, so Escape, the backdrop, the close control and Cancel are one path out; the caller keeps the open state and closes the dialog itself once the action succeeds, so a failure leaves it open with the message. The `error` slot is why this is a component rather than two copies of the same JSX: `RecordingCard` used to render its delete failure in the page behind the modal, where it was invisible until the dialog was dismissed, and `AvatarSection` needed an `!isRemoveModalOpen` guard to stop the same message rendering twice. Its five props are always the ones `useConfirmAction()` (`src/lib/useConfirmAction.ts`) returns, spread straight through — the two call sites no longer keep their own `isOpen`/`isPending`/`error` state. Used by `RecordingCard` (delete a recording) and `AvatarSection` (remove the avatar).
  - `components/ui/UserAvatar.tsx` — the avatar image when `hasAvatar`, initials from `getInitials(name, email)` otherwise, in two sizes (`header` → HeroUI `sm`, `profile` → `lg`). Keyed `hasAvatar ? 'image' : 'fallback'`: Radix's `Avatar` tracks image-loading status on the root and never resets it when `Avatar.Image` unmounts, so without the key change a removed avatar leaves the root stuck reporting "loaded" and the fallback initials never render. It lives in `ui/` rather than `profile/` because `layout/AppHeader` renders it on every authenticated route — keeping it under `profile/` pointed the header at a feature folder. Also used by `profile/page.tsx` and `AvatarSection`.
  - `components/layout/PageShell.tsx` — the full-height gradient background wrapper (`bg-linear-to-br from-accent/10 via-background to-background`). The one file that carries that class string; `AppShell` and `AuthShell` wrap their content in it. `DashboardShell` does not — the dashboard design's background is a flat color, not this gradient.
  - `components/layout/BrandHeader.tsx` — the header bar itself: the app logo/name (as the page's `h1`) wrapped in a HeroUI `Link` to `/` on the left, and a right-hand `children` slot. `sticky top-0 z-20` — below every HeroUI modal's `z-index: 50`, but above ordinary page content — so it stays pinned to the viewport on a page long enough to scroll (the meeting detail page, in particular) rather than scrolling away with the content underneath it. Rendered empty-slotted by `AuthShell` (sign-in and registration have no user to show) and slot-filled by `AppHeader`.
  - `components/layout/AppHeader.tsx` — the authenticated header: `BrandHeader` plus, in its slot, a `UserAvatar` and the display name (falling back to `email`) wrapped in a HeroUI `Link` to `/profile` — a link, but a standalone control, so it takes `touchTarget({ fit: 'block' })` like the button beside it, which already sets the row's height — and a "Sign out" `Button`. Purely presentational — `email`/`onSignOut` are required props, since it only renders where a session exists — and rendered in exactly one place, `AppShell`.
  - `components/layout/AppShell.tsx` — `PageShell` + `AppHeader` (`user`/`signOut` from `useAuthenticatedUserContext()`, the avatar and display name from `useProfileQuery()`) + the centered `max-w-2xl` content container, used by `(workspace)/layout.tsx`. Being in a layout, it is also the profile query's permanent observer for that group: it holds the cache entry alive for as long as `(workspace)` is mounted, which is what keeps `GET /users/me` to one request per session and stops the header's avatar from dropping back to initials on every navigation.
  - `components/layout/AuthShell.tsx` — `PageShell` + `BrandHeader` + the centered `max-w-md` card slot, used by `(auth)/layout.tsx`.
  - `components/layout/AuthenticatedUserProvider.tsx` — calls `useAuthenticatedUser()` once for the whole authenticated route group (both `(dashboard)` and `(workspace)`), renders the single `if (!user) return <LoadingState variant="page"/>` guard screen until the client-side check resolves, and puts the result (`user` narrowed to non-null, plus `signOut` and `applyAccessToken`) on a context read via the exported `useAuthenticatedUserContext()`. The profile is deliberately not on this context: it is a query (`src/lib/queries/profile.ts`) any component reads directly, so a page needing only the profile no longer depends on the session provider at all.
  - `components/layout/QueryProvider.tsx` — mounts `QueryClientProvider` with the client from `createQueryClient()` (`src/lib/queries/client.ts`), held in `useState` rather than at module scope so the server never shares one client — and therefore one user's cached data — between requests. Rendered by the root layout, above both route groups.
  - `components/layout/AppErrorState.tsx` — the shared body of every `error.tsx` under `(app)`: a "Something went wrong" `Card` with the error message and a "Try again" `Button` calling Next's `reset()`, `console.error`ing the error once in an effect. Used by `(app)/error.tsx`, `(dashboard)/error.tsx` and `(workspace)/error.tsx`.
  - `components/layout/DashboardShell.tsx` — the dashboard redesign's chrome, used by `(dashboard)/layout.tsx`: `AppSidebar` (`hidden lg:flex`) beside a column of `AppTopBar` (`hidden lg:flex`) / `MobileTopBar` (`lg:hidden`) plus `children`, `MobileBottomNav` (fixed, `lg:hidden`) and `MobileNavDrawer`. Reads the same session/profile data `AppShell` does and owns one piece of real state — the drawer's open flag, toggled by `MobileTopBar`'s menu button and cleared by the drawer's backdrop/close button.
  - `components/layout/AppSidebar.tsx` — the desktop nav rail (244px, `bg-nav`): brand mark, a `SidebarNavItem` list (only "Meetings" is a real, active link — "Overview"/"Tasks"/"People" render inert, matching the mockup's pages this app doesn't have), and a footer of `SidebarStorageUsage` + `SidebarUserProfile`.
  - `components/layout/AppTopBar.tsx` — the desktop top bar: static page title/breadcrumb ("Meetings" / "Workspace / Meetings" — this shell only ever renders on `/`), a static search field and a static notification bell (no search/notifications feature exists).
  - `components/layout/MobileTopBar.tsx` — the mobile top bar: brand, a static bell, and a real "Open menu" button that opens `MobileNavDrawer`.
  - `components/layout/MobileBottomNav.tsx` — the mobile bottom nav, mirroring `AppSidebar`'s nav list (only "Meetings" real/active).
  - `components/layout/MobileNavDrawer.tsx` — the mobile drawer (`isOpen`/`onOpenChange`, real): a decorative `aria-hidden` backdrop plus a close (X) button both call `onOpenChange(false)`; content is the same nav list, `SidebarStorageUsage` and `SidebarUserProfile` `AppSidebar` renders.
  - `components/layout/SidebarNavItem.tsx` — one nav row (icon + label), shared by `AppSidebar` and `MobileNavDrawer`: `isActive` renders a real `Link` with the tinted/bold treatment, otherwise an inert `<div aria-disabled>`.
  - `components/layout/SidebarStorageUsage.tsx` — the storage-usage card: fully static, no props, no data source — there is no per-user storage quota to report yet.
  - `components/layout/SidebarUserProfile.tsx` — the sidebar/drawer's account row: initials + name/email (same data `AppHeader` reads) linking to `/profile`, plus a HeroUI `Dropdown` overflow menu whose only item is "Sign out" (the existing `onSignOut`) — the mockup draws this row with no visible sign-out control, so its trigger moved into the "…" menu rather than being dropped.
  - `components/meetings/CreateMeetingModal.tsx` — a HeroUI `Modal.Backdrop`/`Form` (controlled via `isOpen`/`onOpenChange`) for creating a meeting by hand: `title` (required, inline error if blank), `date` (native `<input type="datetime-local">`, required, converted via `new Date(value).toISOString()` on submit), `participants` (split on `,` and trimmed into a string array, `[]` — never omitted — when blank, since `CreateMeetingDto.participants` has no `@IsOptional()`). All three are `TextInputField`s on the shared form convention: a blank title or date fails that field's `validate`, so the form blocks its own submit, focuses the first invalid field and shows the message in its `FieldError` — the modal no longer keeps `titleError`/`dateError` state or wires `Label htmlFor` to `Input id` by hand. On success it calls `createMeeting()` (`src/lib/api.ts`), then the caller-supplied `onCreated(meeting)` and closes itself; on failure `toFormErrorState` puts the `ApiError` message on the form-level `ErrorText` and it stays open. Closing it resets every field and both error slots. Not scoped to any existing meeting — used only by `page.tsx`.
  - `components/meetings/RecentMeetingCard.tsx` — one card in the home page's "Recent meetings" grid, sized responsively (`lg:` variants, not a separate mobile component): a `MeetingStatusBadge`, title, participants line (standing in for the mockup's description, which has no backing field), date, and either an "Upload recording" pill (`recordingCount === 0`, opens `UploadRecordingModal` via `useMeetingUploadModal`) or an "Open summary" link to the meeting (`recordingCount > 0`). Stretched-link pattern: the title `Link`'s `after:absolute after:inset-0` covers the (`relative`) card, and the action row is a later, `relative` sibling so it paints above that overlay and stays clickable.
  - `components/meetings/MeetingTableRow.tsx` — one row of the desktop "All meetings" table (`hidden lg:block`): an icon tile (one consistent icon for every row — the mockup's per-row icon implies a categorization the API doesn't have) + stretched link to the meeting, date, participants, files (`recordingCount`), a `MeetingStatusBadge` (success "Uploaded" / warning "Needs upload"), and an actions cell whose `Dropdown` has one item, "Upload recording" (only while `recordingCount === 0`, via `useMeetingUploadModal`) — decorative, non-interactive when a recording already exists.
  - `components/meetings/MeetingListRow.tsx` — the mobile equivalent (`lg:hidden`) of `MeetingTableRow`: icon tile, stacked title + "date · N files" line, `MeetingStatusBadge`, same actions menu.
  - `components/meetings/MeetingStatusBadge.tsx` — the success/warning status pill shared by `MeetingListRow`, `MeetingTableRow` and `RecentMeetingCard`: `hasRecording` picks the tone, `pendingLabel`/`readyLabel` supply each call site's own text ("Needs upload"/"Uploaded" on the two all-meetings rows, "Recording needed"/"Summary ready" on the recent-card), `showDot` renders the small leading status dot the compact mobile row omits, and `className` carries each call site's own sizing. Replaces three copies of the same conditional class string.
  - `components/meetings/UploadRecordingModal.tsx` — a HeroUI `Modal.Backdrop` (controlled via `isOpen`/`onOpenChange` props, no `<Modal>` trigger wrapper) around `RecordingUploader`, used by `RecentMeetingCard`, `MeetingTableRow` and `MeetingListRow` for uploading without leaving the list — all three spread `useMeetingUploadModal()`'s return value straight onto it.
  - `components/meetings/RecordingUploader.tsx` — the upload area, matching the design's "Recording Upload Zone" (`Mn57N`): a solid-bordered box (an accent-tinted border while dragging over it) with an accent-soft icon circle, a "Drop a recording here" heading, a single muted helper line ("or choose a file · {constraints}"), and a dark primary "Choose file" button, plus a hidden `<input type="file">` and native drag-and-drop handlers. It owns only the drag-over highlight and the JSX; the hidden input, the client-side check against `RECORDING_UPLOAD` from `src/lib/uploads.ts` (the mirror of `apps/api/.env`'s `ALLOWED_RECORDING_MIME_TYPES`/`MAX_UPLOAD_SIZE_BYTES`), progress and cancellation come from `useFileSelection` in `'immediate'` mode, bound to `uploadMeetingRecording`. A drop and a picked file both go through the hook's `selectFile`, so the "ignore a file that arrives mid-upload" guard applies to both without being written here. It shows a HeroUI `ProgressBar` during upload with a "Cancel" button calling the hook's `cancelUpload` (an `AbortController` abort), and an inline error message (from `ApiError`, or the client-side validation message) otherwise. Used by both `/meetings/[id]/page.tsx` (rendered unconditionally below the recordings list, so a meeting with zero or several files can always accept another) and `UploadRecordingModal` (inside a modal, itself used by the dashboard's recent cards and all-meetings rows too).
  - `components/meetings/RecordingCard.tsx` — one recording's compact tile, keyed by `recording.id`, with no always-visible player: a ghost `Button` (`touchTarget="block"`, so a wrapped filename grows it rather than clipping) holding the play icon, the filename and, on a second line inside the same label, the human-readable size and upload date — `onPress` opens `RecordingPlayerModal`. It used to be an `href`-less HeroUI `Link onPress`, which announced itself as a link that went nowhere, with the meta line as a sibling `<p>` outside the control; a button is what it always was, and folding the meta line into its label is what keeps that line inside the target instead of beside it. - `src/lib/api.ts` — thin `fetch` wrapper for calling `apps/api`: reads the base URL from `NEXT_PUBLIC_API_URL` (env var, see below), exposes `registerUser`, `loginUser`, `createMeeting(title, date, participants)`, `getMeetings`, `getMeeting`, `deleteMeetingRecording(meetingId, recordingId)`, `getRecordingContentUrl(meetingId, recordingId)`, and the users half — `getProfile`, `updateProfile(name)`, `changePassword(currentPassword, newPassword)`, `getAvatarUrl(avatarUpdatedAt)`, `uploadAvatar(file, opts)` and `deleteAvatar()` (all attaching `Authorization: Bearer <token>` via `getAccessToken()` from `src/lib/auth.ts`, except the two URL builders, `getRecordingContentUrl` and `getAvatarUrl`, which append the token as a `?token=` query param instead, since a `<video>` or `<img>` element's `src` can't set request headers and the API's `JwtAuthGuard` accepts either form — `getAvatarUrl` also appends `v=avatarUpdatedAt`, so a replaced avatar busts the browser's cache instead of re-showing the previous file at the same URL), and throws `ApiError` (with the HTTP status and the API's `message`) on non-2xx responses. The shared `handleResponse` returns `undefined` for a 204 (no body to parse) rather than always calling `response.json()`, so `deleteMeetingRecording` can reuse it like every other function here instead of hand-rolling its own error handling. `uploadMeetingRecording(meetingId, file, opts)` and `uploadAvatar(file, opts)` are the exception to the shared `fetch`-based `handleResponse` plumbing: both are built on `XMLHttpRequest` because `fetch` exposes no upload-progress events, posting to `/meetings/:id/recordings` and `/users/me/avatar` respectively and both taking the exported `UploadOptions` (`{ onProgress, signal }`) — one declaration for both XHR uploaders, so `useFileSelection` types its `upload` prop against it instead of restating the shape (an `AbortSignal` cancels the in-flight `XMLHttpRequest`, rejecting with `UploadCancelledError` rather than `ApiError` so callers can distinguish a user-initiated cancel from a real failure) and reusing the same error-message extraction as the rest of the file.
- `src/lib/auth.ts` — client-side-only auth state, backed by `localStorage` (key `accessToken`, no cookie/session — nothing server-side reads it yet, so there's no SSR/middleware auth gate, only the client-side check via `useAuthenticatedUser`). `storeAccessToken`/`clearAccessToken` write/clear the token, `getAccessToken()` reads the raw token (used by `src/lib/api.ts` to authenticate requests); `getStoredUser()` decodes the JWT's payload (base64, no signature verification — the API is the source of truth) and returns `{ email }`, or `null` if missing/expired (`exp` claim), self-clearing the stored token when expired.
- `src/lib/useAuthenticatedUser.ts` — `useAuthenticatedUser()`, the token half of the client-side session: it redirects to `/login` once the session query resolves to nothing valid, and otherwise exposes `{ user, signOut, applyAccessToken }`; `user` stays `null` until the check resolves. It owns the token concern only — the profile is a separate query this hook neither fetches nor holds. The stored-token check is re-run (`refetchQueries` on `sessionQueryKey`) on every `usePathname()` change, because the provider that owns the hook sits in a layout Next.js keeps mounted across in-group navigation — without it an expired token would go unnoticed until a full page load; an unchanged session re-reads to an equal object, and the query cache's structural sharing keeps the previous reference, so navigating invalidates nothing downstream. `signOut` clears the token, clears the whole query cache (nothing of one session may survive into the next one signed in on this tab) and redirects; `applyAccessToken` stores a reissued token and writes the user decoded from it straight into the session cache entry. It is called in exactly one place — `AuthenticatedUserProvider`.
- `src/lib/queries/` — the TanStack Query layer. `client.ts` exports `createQueryClient()`, whose app-wide defaults are `retry: false` (`src/lib/api.ts` throws `ApiError` carrying the API's own message, which the UI renders as-is; retrying a 401/404 only delays it) and `refetchOnWindowFocus: false`; freshness is deliberately left per-query rather than set globally. `session.ts` holds `sessionQueryKey`, `useSessionQuery()` — `getStoredUser()` as a query, so the reissued-token path can write to it with `setQueryData`, and so the `localStorage` read happens after mount (a query function never runs during render, so the server-rendered markup and the first client render agree) — and `useResetQueryCache()`, called at each session boundary by `/login`, `/register` and `signOut`; without the reset on sign-in, the previous session's cached "no valid token" answer would bounce the freshly signed-in user straight back to `/login`. `profile.ts` holds `profileQueryKey`, `useProfileQuery()` (`{ profile, profileError }`, `staleTime: Infinity`), `useApplyProfile()`, which merges a `Partial<Profile>` into the cached profile with `setQueryData`, and `ProfileSaved` — the one payload the three `/profile/edit` sections hand back through their shared `onSaved` callback (`{ profile?: Partial<Profile>; accessToken?: string }`, each section filling only the half it produced, `profile/edit/page.tsx` dispatching each half to `useApplyProfile()` and to the session's `applyAccessToken`). That merge is a delta against whatever is cached at the moment it runs, not a whole `Profile` built from a copy read earlier: an avatar upload can resolve long after it read the profile, by which point another section may have saved a newer one. `meetings.ts` holds the meetings half: `meetingsQueryKey` (`['meetings', 'list']`) and `meetingQueryKey(id)` (`['meetings', 'detail', id]`) — sibling branches rather than the detail nesting under the list, so invalidating one meeting never drags the list along; `useMeetingsQuery()` (`{ meetings, meetingsError }`, default freshness, so returning to `/` revalidates from the cache instead of blinking back to a spinner); `useAddCreatedMeeting()` and `useCountUploadedRecording()`, the two `setQueryData` writes the list accepts (a created meeting prepended with `recordingCount: 0`, an uploaded recording counted on one entry); and `useMeetingDetailQuery(id)`, which returns `{ meeting, meetingError, isSummaryPending, showSummarySection, onRecordingUploaded, onRecordingDeleted }`. Its `refetchInterval` is the callback form — it is handed the cached meeting on every scheduling decision, refetches every 4 seconds while `isMeetingSettled()` is false, and stops on its own the moment the meeting settles or a refetch fails (an API that just failed is not worth polling; the page shows that error inline). Both callbacks `setQueryData` the recording they know about into (or out of) the cached meeting and then `invalidateQueries` that meeting for everything else; the invalidation is also what retires the page's old `pollGenerationRef` stale-response guard, since it cancels an in-flight poll before refetching, so a response already on its way when the user uploaded or deleted can no longer land on top of the newer state. `onRecordingDeleted` additionally calls the reconciliation reset (below) — a deletion can invalidate the summary in a way the leftover recordings' statuses don't show. The cache write is what makes that reset stick: `invalidateQueries` does not clear `data`, so a reset measured against the still-cached pre-deletion recordings would be re-advanced on the very next render.
- `src/lib/format.ts` — the display formatters, each defined once: `formatDateTime()`, the single `Intl.DateTimeFormat('en-US', { dateStyle: 'medium', timeStyle: 'short' })` used everywhere a meeting or recording timestamp is displayed (`RecentMeetingCard`, `MeetingTableRow`, `MeetingListRow`, `RecordingCard`, `meetings/[id]/page.tsx`); `formatFileSize(sizeBytes)`, which turns the API's string byte count into the largest unit above 1 (bytes whole, KB/MB/GB to one decimal, `'Unknown size'` for an unparseable value) for `RecordingCard`; `getGreeting(date?)`, the dashboard header's time-of-day greeting ("Good morning"/"afternoon"/"evening" from `date.getHours()`, defaulting to `new Date()`) used only by `(dashboard)/page.tsx`; and `getInitials(name, email)`, the avatar placeholder text (up to two initials from the display name, falling back to the email's local part) used by `UserAvatar` and `SidebarUserProfile`.
- `src/lib/touchTarget.ts` — `touchTarget`, the one `tailwind-variants` recipe expressing the app's 44px (mobile) / 40px (desktop) minimum, in four `fit` shapes: `height` (the default, `h-11 md:h-10`), `block` (`h-auto min-h-11 md:min-h-10`, for a control whose own content decides its height), `square` (`size-11 md:size-10`, for an icon-only control) and `inset` (`h-full w-11 md:w-10`, for a control filling a container that is already one target tall — the `PasswordField` eye toggle, which pinned to 44px would overflow the field's border box by the width of its border). It replaced the three spellings this used to have — `h-11 md:h-10` hand-written per call site, HeroUI's `size="lg"` (which happens to compile to the same heights), and `min-h-[44px] md:min-h-10` — so the minimum is a mechanism rather than a convention. `components/ui/Button.tsx` applies it to every button; `TextInputField`, `PasswordField`, `RecordingCard`'s "Transcribing…" slot (which has to line up with the toggle that replaces it) and `AppHeader`'s `/profile` link call it directly. Deliberately out of scope: a link that is inline text inside a sentence (the auth pages' "Create one"/"Sign in" footers), where padding to 44px would break the line it sits in. The classes are Tailwind utilities on purpose — HeroUI ships its control heights in the `components` cascade layer, which `utilities` overrides, so they win without `!important`.
- `src/lib/validation.ts` — the shared client-side input rules, each stated once with its message so no two forms can word the same rule differently. `validateEmail(value)` (a blank field and a malformed address distinguished, over a deliberately permissive module-private `EMAIL_PATTERN` — the API validates for real; this only catches an obvious typo before a request is made) is the whole `validate` prop of the email field on both `/login` and `/register`. `validatePasswordLength(value)` and the `PASSWORD_LENGTH_HINT` shown under the field are the client half of `apps/api/src/auth/password-rules.ts`'s `MIN_PASSWORD_LENGTH` (also exported, for the field's `minLength` attribute), used by `/register` and `PasswordSection` — checking it client-side is part of what leaves a 400 from `PUT /users/me/password` meaning only "the current password is wrong". `MAX_DISPLAY_NAME_LENGTH` mirrors `@MaxLength(100)` on `name` in `apps/api/src/users/dto/update-profile.dto.ts` and caps the `DisplayNameSection` input.
- `src/lib/formErrors.ts` — how a failed request becomes something a form can display. `FormErrorState` is the pair every form holds (`formError`, the line rendered as an `ErrorText` under the fields, and `fieldErrors`, handed straight to HeroUI's `Form` as `validationErrors`), `NO_FORM_ERRORS` the cleared value it starts from, and `toFormErrorState(error, fallbackMessage, fieldByStatus)` the conversion. The attribution to a field is declared at the call site as a status→field map and is keyed by HTTP status and nothing else: `apps/api` returns no machine-readable error code, and the approach this replaced — `PasswordSection` regex-matching `/current password is incorrect/i` against the API's prose — would have silently degraded to a form-level error the day that sentence was reworded. A status the map does not name, and any failure that is not an `ApiError`, falls back to the form-level line. Today two call sites use the map: `/register` maps 409 (`Email is already registered`) to `email`, and `PasswordSection` maps 400 to `currentPassword`.
- `src/lib/meetings.ts` — the meeting domain rules, all pure: `parseParticipants(value)`, splitting the create-meeting form's free-text participants field on `,`, trimming each entry and dropping blanks, so a trailing comma yields `[]` rather than an empty participant (used by `CreateMeetingModal`); `recordingsSignature(meeting)`, the order-independent `id:status` fingerprint of a meeting's recordings; `isMeetingSettled(meeting)`, true when no recording is still `UPLOADED`/`PROCESSING` **and** the summary has caught up with the ones that are left — `summary.status === 'FAILED'`, or `summary === null` with no `READY` recording, or `summary.status === 'READY'` **and** `summary.foldedRecordingIds` matching every currently-`READY` recording id (order-independently, via the module-private `sameRecordingIds`). That last condition is the one that needs its own check rather than trusting `status === 'READY'`: `apps/api`'s `update_meeting` agent tool can briefly settle `MeetingSummary.status` to `READY` mid-fold without updating `foldedRecordingIds` (see `docs/architecture/api.md`), and that transient snapshot would otherwise read as "caught up", stopping the polling before the fold's real, final write (with the complete `actionItems`) lands — the bug this check exists to close. It is also what makes a _later_ recording transition (a second recording finishing after the first already produced a `READY` summary) read as unsettled. Finally `hasSummarySection(meeting)`, true when a summary row exists or a recording is still on its way to producing one (not yet `FAILED`).
- `src/lib/useMeetingSummaryStatus.ts` — `useMeetingSummaryStatus(meeting)`, the summary-reconciliation hook behind `useMeetingDetailQuery`'s `isSummaryPending`/`showSummarySection`. It keeps the `recordingsSignature` of the recording set the summary was last seen to cover (`reconciledRecordingsSignature`, advanced conditionally _during render_ rather than in an effect — React's "Adjusting state when a prop changes" pattern, without the extra render+commit round-trip), and only advances it once `isMeetingSettled(meeting)` holds; anything the fingerprint doesn't cover is pending, which `MeetingSummarySection` renders as its "Updating — more recordings are still being processed…" banner over the existing content. Its `resetReconciliation()` is called by `useMeetingDetailQuery`'s `onRecordingDeleted`: a deleted recording can leave the cached summary stale relative to the new recording set (deleting the only recording leaves an empty, vacuously "all terminal" list), so the fingerprint is cleared and the summary is re-measured against the post-deletion recordings — which `onRecordingDeleted` has already removed from the cached meeting, without which the cleared fingerprint would just be re-advanced against the stale copy — rather than the page trusting a summary it can no longer vouch for.
- `src/lib/uploads.ts` — `RECORDING_UPLOAD` and `AVATAR_UPLOAD`, both `UploadConstraints` (`allowedMimeTypes`, `allowedExtensionsLabel`, `maxSizeBytes`, `maxSizeLabel`): the client-side mirror of `apps/api/.env`'s `ALLOWED_RECORDING_MIME_TYPES`/`MAX_UPLOAD_SIZE_BYTES` and `ALLOWED_AVATAR_MIME_TYPES`/`MAX_AVATAR_SIZE_BYTES`. They drive the file picker's `accept`, the "…· up to …" hint and the client-side rejection messages in `RecordingUploader` and `AvatarSection`; no component declares an upload MIME type or size constant of its own. `validateFile(file, constraints)` lives here too — the one client-side type/size check, called only by `useFileSelection`, so both uploaders reject an over-size or wrong-type file with the same wording.
- `src/lib/useFileSelection.ts` — `useFileSelection({ constraints, mode, upload, onUploaded })`, the file-picking half of both uploaders: the hidden `<input type="file">` (returned as `inputProps`, spread by the component, reset to `''` after every change so re-picking the same file still fires), `openFilePicker()`/`selectFile(file)` for the picker and drag-and-drop, the one `validateFile` call, `progress`/`isUploading`, `cancelUpload()` and the `error` line. `mode: 'immediate'` uploads as soon as a file arrives (`RecordingUploader`); `mode: 'staged'` keeps the `File` plus a `URL.createObjectURL` preview until `uploadSelectedFile()` (`AvatarSection`'s stage-then-Save, where selecting must not upload on its own), with `clearSelection()` discarding both. Two invariants live here rather than at the call sites, which is why the hook exists: a file arriving while `isUploading` is ignored (one guard, so a fast second pick or a mid-upload drop cannot take the `AbortController` away from the request already running), and a rejection with `UploadCancelledError` returns before any error state is set, so a user-initiated cancel never renders as a failure. The object URL is revoked when a new file replaces it, when the selection is cleared, when the upload fails, and on unmount; a successful upload deliberately keeps it, because it already shows exactly what was stored. Unmounting also aborts an in-flight upload (the same `AbortController` `cancelUpload()` uses) rather than leaving its `.then`/`.catch` to resolve against a component that is gone — the abort rejects with `UploadCancelledError`, which the hook already treats as a no-op, so no state update or `onUploaded` call reaches a gone component.
- `src/lib/useMeetingUploadModal.ts` — `useMeetingUploadModal({ meetingId, onUploaded })`, the open-state and "close then bubble up" mechanics behind every meeting row/card's `UploadRecordingModal`: `open()` plus `isOpen`/`meetingId`/`onOpenChange`/`onUploaded`, spread straight onto the modal. `onUploaded` closes the dialog before calling the caller's `onUploaded`, so `MeetingListRow`, `MeetingTableRow` and `RecentMeetingCard` no longer each hold their own `useState` and inline closure for the same wiring.
- `src/lib/useConfirmAction.ts` — `useConfirmAction({ action, fallbackMessage })`, the open/pending/error mechanics behind every `ConfirmModal`: `open()` and the `isOpen`/`onOpenChange`/`isPending`/`error`/`onConfirm` props handed straight to the dialog. `onConfirm` runs `action` (the request plus whatever local state its success earns — `RecordingCard`'s `onDeleted`, `AvatarSection`'s `selection.clearSelection()`/`setIsRemoved`/`onSaved`), closing the dialog only once it resolves and setting `error` (via `apiErrorMessage`) rather than closing when it rejects; `onOpenChange` clears a stale `error` on every open and close, so Escape, the backdrop and Cancel all leave the dialog the same way a successful confirm does. It replaced three hand-written `useState`s and a `try`/`catch`/`finally` block duplicated identically between `RecordingCard`'s delete flow and `AvatarSection`'s remove flow — only what runs inside `action` ever differed between them.
- `src/app/globals.css` — global styles, pulled in by the root layout as `@/app/globals.css` (the alias, like every other import in `src/` — the co-located `./globals.css` Next.js scaffolds would be the one relative specifier left). Starts with `@import 'tailwindcss';` then `@import '@heroui/styles';` (order matters); the old hand-rolled `--background`/`--foreground` light/dark vars were removed in favor of HeroUI's own theme variables (see below)
- `postcss.config.mjs` — registers the `@tailwindcss/postcss` plugin, required for Tailwind v4

## Component conventions

The decisions that used to be made per component, settled once so a reader can predict a
component's shape before opening it. The rules themselves are in `apps/web/CLAUDE.md`; this is
what they look like in the tree.

- **Callback names.** `onSaved(saved: ProfileSaved)` on all three `/profile/edit` sections;
  `onUploaded(recording: Recording)` on `RecordingUploader`, `UploadRecordingModal`,
  `RecentMeetingCard`, `MeetingTableRow` and `MeetingListRow`; `onDeleted(recordingId)` on
  `RecordingCard`; `onCreated(meeting)` on
  `CreateMeetingModal`. Before this, one save was `onSaved(Profile)`, one `onProfileChange(Partial<Profile>)`
  and one `onChanged(accessToken)`, and `onUploaded` meant a `Recording` in two components and a
  `meetingId` in a third.
- **Modals.** `isOpen` + `onOpenChange(isOpen)`, always caller-owned, never a HeroUI `<Modal>`
  trigger wrapper: `CreateMeetingModal`, `UploadRecordingModal`, `RecordingPlayerModal` and the
  shared `ConfirmModal`, which is the only destructive confirmation in the app.
- **`'use client'`.** Every `.tsx` under `src/components/` opens with it, icons included — there
  are no server components below the root layout, so an "only where it is needed" rule would have
  no observable effect and, being unobservable, is exactly what let `AppHeader`, `UserAvatar`,
  `RecordingStatusChip` and `MeetingSummarySection` drift out of it. `icons/index.ts` is a
  re-export barrel rather than a component and carries no directive.
- **Prop order.** Alphabetical in the props interface, in the destructuring and in the JSX
  attributes at the call site, so a component's declaration and its usages read in one order.
- **Import paths.** The `@/` alias everywhere, including between siblings in the same folder —
  `RecordingCard` imports `@/components/meetings/RecordingStatusChip`, not `./RecordingStatusChip`,
  and `icons/index.ts` re-exports through the alias too. `grep -rn "from './" apps/web/src` is
  expected to come back empty.
- **Placement.** A component used by exactly one page still lives in `src/components/<feature>/`,
  never beside the route: `src/app/` holds routes, so `AvatarSection`, `DisplayNameSection` and
  `PasswordSection` sit in `components/profile/` even though only `/profile/edit` renders them.

## Calling apps/api

`NEXT_PUBLIC_API_URL` (see `.env.example`, defaults to `http://localhost:3001` in `src/lib/api.ts` if unset) is the base URL `src/lib/api.ts` calls. It must be prefixed `NEXT_PUBLIC_` to be readable in client components (Next.js only inlines env vars with that prefix into the browser bundle). It must point at `apps/api`'s port (`PORT` in `apps/api/.env`, default `3001`).

## HeroUI v3

- Packages: `@heroui/react`, `@heroui/styles`, `tailwind-variants`, plus `tailwindcss`/`@tailwindcss/postcss`/`postcss` for the Tailwind v4 base it builds on.
- No provider component is needed (unlike HeroUI v2's `HeroUIProvider`).
- Components use compound composition (e.g. `Card.Header`) and `onPress` instead of `onClick`; import from `@heroui/react`.
- Theming is CSS-variable/`oklch`-based via `@heroui/styles`, switching on `[data-theme='dark']`/`[data-theme='light']` rather than `prefers-color-scheme`. No theme switcher is wired up yet — the app currently renders HeroUI's default light theme (`:root`'s values apply with no `data-theme` attribute set), except `src/app/globals.css` darkens HeroUI's default `--accent`/`--muted` tokens to meet WCAG AA contrast (4.5:1) — HeroUI's originals fell short for button text on `--accent` and placeholder text on `--muted`.

## Lint

ESLint config (`eslint.config.mjs`) composes `eslint-config-next`'s `core-web-vitals` and `typescript` rule sets via the flat-config `defineConfig` helper, then adds the app's own structural rules — the half of `apps/web/CLAUDE.md`'s conventions a machine can check, so they fail `pnpm lint:web` instead of review:

| Block                                  | Applies to                      | Forbids                                                                                      |
| -------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------- |
| `web/module-paths-use-the-alias`       | `src/**`                        | every relative specifier (`.`, `..`, `./*`, `../*` and below) — imports use the `@/` alias   |
| `web/routes-do-not-render-the-header`  | `src/app/**`                    | importing `@/components/layout/AppHeader` — the header is the group layout's, via `AppShell` |
| `web/meetings-does-not-import-profile` | `src/components/meetings/**`    | `@/components/profile/*`                                                                     |
| `web/profile-does-not-import-meetings` | `src/components/profile/**`     | `@/components/meetings/*`                                                                    |
| `web/layout-does-not-import-features`  | `src/components/layout/**`      | `@/components/meetings/*`, `@/components/profile/*`                                          |
| `web/ui-primitives-know-no-feature`    | `src/components/ui/**`          | `@/components/meetings/*`, `@/components/profile/*`, `@/components/layout/*`                 |
| `web/error-text-owns-the-danger-class` | `src/**` except `ErrorText.tsx` | the literal or template string `text-sm text-danger` (`no-restricted-syntax`)                |

`no-restricted-imports` matches the specifier string a file writes, not the module it resolves to,
which is why the alias rule comes first and every folder-scoped block below restates it: without
it each seal would see only the `@/` spelling of a forbidden import and let `../profile/Section`
through. Flat config replaces a rule's options rather than merging them, so a block that named
only its own patterns would switch the alias rule back off for that folder.

Each was checked by introducing the violation it names — in both the alias and the relative
spelling — and confirming `pnpm lint:web` fails on it.
The conventions that are _not_ mechanically checkable — callback names, prop order, the form
convention, where server state lives — stay prose in `apps/web/CLAUDE.md`.
