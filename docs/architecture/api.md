# apps/api — architecture reference

The per-file, per-class inventory of the NestJS backend. It used to live in
`apps/api/CLAUDE.md`, where every session loaded all 33 KB of it before doing anything.
Read the part you need; `apps/api/CLAUDE.md` keeps the rules and the boundaries.

## Modules and files

- `src/main.ts` — bootstraps `AppModule` via `NestFactory`; enables CORS restricted to `WEB_URL` (default `http://localhost:3000`) so `apps/web` can call this API from the browser
- `src/app.module.ts` — root module. Imports `ConfigModule` (global), `PrismaModule`, `StorageModule`, `UsersModule`, `AuthModule`, `MeetingsModule`, `TasksModule`, `McpModule`; registers a global `ValidationPipe` (`whitelist: true, transform: true`) via `APP_PIPE`. `TranscriptionModule`/`MeetingSummaryModule`/`ClaudeAgentModule` are not imported here — they're imported directly by `MeetingsModule` (`TranscriptionModule`, `MeetingSummaryModule`) and by `MeetingSummaryModule` (`ClaudeAgentModule`), the only modules that use them (see below)
- `src/prisma/` — `PrismaModule` (`@Global()`) and `PrismaService`, a `PrismaClient` subclass connected via the `@prisma/adapter-pg` driver adapter (Prisma 7 requires a driver adapter; the connection string can no longer live in `schema.prisma`), reading `DATABASE_URL` through `ConfigService`. Connects on `onModuleInit`, disconnects on `onModuleDestroy`
- `src/storage/` — `StorageModule` (`@Global()`) and `StorageService`, a single local-filesystem implementation (`save`/`createReadStream`/`delete`/`exists`) reading `UPLOADS_DIR` through `ConfigService`. `save(meetingId, { originalFilename, buffer })` writes to `{UPLOADS_DIR}/{meetingId}/{uuid}{ext}` (extension derived from `originalFilename`) and returns the resulting absolute `storagePath`; `createReadStream` accepts an optional `{ start, end }` byte range for future HTTP Range support; `exists`/`delete` operate on a `storagePath` previously returned by `save`; `delete` also removes the parent directory if it's left empty (silently keeps it if other files remain). Deliberately HTTP-agnostic (no dependency on `Express.Multer.File` or any route) so it can be unit-tested and reused by whichever upload/streaming routes are wired on top of it. Path resolution is id-kind-aware: `resolveMeetingDir(meetingId)` returns `{UPLOADS_DIR}/{meetingId}` and `resolveAvatarDir(userId)` returns `{UPLOADS_DIR}/avatars/{userId}` (namespaced under `avatars/` so a meeting id and a user id can never collide on the same path), both going through a shared private `assertValidId` guard that rejects anything that isn't a plain UUID — the id can come straight from a URL param or JWT payload, and without this check a value like `..\..\Temp` would resolve outside `UPLOADS_DIR` via `path.join`'s normal `..` handling. `pruneMeetingDir(meetingId, keepStoragePath)` and `pruneAvatarDir(userId, keepStoragePath)` both delegate to a shared private `pruneDir(dir, keep)` that removes every other file in the resolved directory, based on the actual directory listing taken _after_ the caller's DB upsert commits (not a pre-upsert snapshot) — race-free cleanup for concurrent uploads to the same meeting/user, best-effort (a failure removing one stray file doesn't fail the others or throw). `upload-multer-options.factory.ts`'s `createUploadMulterOptions` is the shared `MulterModule.registerAsync` factory body used by both `MeetingsModule` (recordings) and `UsersModule` (avatars): given a `resolveDir(req)` closure, an `isAllowedFile` allowlist check, `maxFileSizeBytes` and `allowedMimeTypes`, it builds the `diskStorage` (`destination` creates/uses the resolved dir, `filename` via `StorageService.generateFilename`), `limits.fileSize` and `fileFilter` (415 via `UnsupportedMediaTypeException` on an allowlist miss) — only how the destination directory and allowlist are derived differs per route.
- `src/users/` — `UsersModule`, the sole owner of user persistence, importing `AuthModule` to reuse `JwtAuthGuard`/`@CurrentUser()`. `users.repository.ts` (`UsersRepository`, a thin Prisma wrapper: `findByEmail`, `findById`, `create`, `updateName`, `updatePassword`) is a module-private provider — it is **not exported**; other modules reach it only by dispatching `CreateUserCommand` (`commands/create-user.command.ts` + `commands/handlers/create-user.handler.ts`) or `FindUserByEmailQuery` (`queries/find-user-by-email.query.ts` + `queries/handlers/find-user-by-email.handler.ts`) through `CommandBus`/`QueryBus`. `UsersModule` is imported directly by `AppModule` (not by `AuthModule`) so its handlers are registered in the module graph independently of who calls them. It also owns the own-profile read/write path: `GetProfileQuery` (`queries/get-profile.query.ts` + `queries/handlers/get-profile.handler.ts`) looks up a user by id (404 if missing) and `UpdateProfileCommand` (`commands/update-profile.command.ts` + `commands/handlers/update-profile.handler.ts`) persists a new display name via `updateName`; both return a `ProfileResponse` (`interfaces/profile-response.interface.ts`, via `toProfileResponse`). `dto/update-profile.dto.ts`'s `UpdateProfileDto` validates the HTTP body (`name?: string | null`, `@MaxLength(100)`) and trims it via a `class-transformer` `@Transform`, collapsing a blank string to `null` before validation runs. `UsersRepository.updateName` returns `null` (rather than throwing) if the user row is already gone — mirrors `RecordingsRepository.delete`'s P2025-swallowing pattern — so `UpdateProfileHandler` can turn that into the same `NotFoundException` (404) `GetProfileHandler` throws for a missing user, instead of letting Prisma's error surface as a 500. `UsersController`, guarded with `@UseGuards(JwtAuthGuard)` at the class level (`GET /users/me` → 200, `PATCH /users/me` → 200/400/404, `POST /users/me/password` → 200/400/401), resolves the target user strictly from `@CurrentUser()`'s `user.sub` — never from a route param — so a caller can only ever read/write their own profile; it depends only on `CommandBus`/`QueryBus`, dispatching `GetProfileQuery`/`UpdateProfileCommand`/`ChangePasswordCommand`. A `PATCH` body that omits `name` entirely (`dto.name === undefined`, distinct from an explicit blank string, which the DTO's `@Transform` already normalizes to `null`) is treated as a no-op read — the controller dispatches `GetProfileQuery` instead of `UpdateProfileCommand` — so a partial-update request can never accidentally wipe a previously-set name. `UsersRepository.updatePassword` persists a new hashed password by id, mirroring `updateName`'s P2025-swallowing `null`-on-missing-row behavior. `commands/change-password.command.ts` + `commands/handlers/change-password.handler.ts` — `ChangePasswordCommand`/`ChangePasswordHandler`: verifies `currentPassword` against the stored hash via `bcrypt.compare` (`BadRequestException`/400 on mismatch), rejects a `newPassword` equal to `currentPassword` (via `auth/password-rules.ts`'s `isDifferentFromCurrent`, 400), hashes the new password with the shared `PASSWORD_SALT_ROUNDS` constant (also used by `RegisterUserHandler`, so both hash identically) and persists it via `updatePassword`, then signs and returns a fresh `AccessTokenResponse` via `TokenService` so the caller's session survives the change without a re-login. `dto/change-password.dto.ts`'s `ChangePasswordDto` validates the HTTP body (`currentPassword: string`, `newPassword: string` with `@MinLength(MIN_PASSWORD_LENGTH)`, both from `auth/password-rules.ts`). The route is `@Post('me/password')` with `@HttpCode(HttpStatus.OK)` since Nest defaults `POST` handlers to 201. **Avatar upload/delete:** `UsersModule` imports `MulterModule.registerAsync({ inject: [ConfigService, StorageService], useFactory: ... })`, delegating to `storage/upload-multer-options.factory.ts`'s `createUploadMulterOptions` (shared with `MeetingsModule`'s recording upload — see the storage bullet above) with `resolveDir` reading the authenticated user's id off `req.user.sub` (set by `JwtAuthGuard`, which runs before any interceptor, so it's already populated when multer's `destination` callback fires) rather than a route param, `MAX_AVATAR_SIZE_BYTES` for `limits.fileSize`, and `avatar-file-filter.ts`'s `isAllowedAvatarFile`/`ALLOWED_AVATAR_MIME_TYPES` for the allowlist (415 via `UnsupportedMediaTypeException`, bootstrap-time `assertKnownAvatarMimeTypes` guard, mirroring `recording-file-filter.ts`). `UsersController.uploadAvatar` (`@Post('me/avatar')`, `@UseInterceptors(FileInterceptor('file'))`) throws `BadRequestException` (400) when `req.file` is `undefined`, mirroring `MeetingsController.uploadRecording`; `deleteAvatar` is `@Delete('me/avatar')` → 204. `user-avatars.repository.ts`'s `UserAvatarsRepository` (thin Prisma wrapper: `findByUserId`, `createOrReplace` — an upsert keyed on the unique `userId` — `delete`, the last two mirroring `RecordingsRepository`'s P2025-swallowing pattern) is declared directly in `UsersModule` (no other module needs it). `commands/upload-avatar.command.ts` + `commands/handlers/upload-avatar.handler.ts` — `UploadAvatarCommand`/`UploadAvatarHandler`: `createOrReplace`s the DB row from the file multer already wrote to disk, then calls `StorageService.pruneAvatarDir(userId, avatar.storagePath)` to remove any other file left in the user's avatar directory — race-free cleanup for concurrent uploads, exactly mirroring `UploadRecordingHandler`'s use of `pruneMeetingDir`. `commands/delete-avatar.command.ts` + `commands/handlers/delete-avatar.handler.ts` — `DeleteAvatarCommand`/`DeleteAvatarHandler`: 404 when `UserAvatarsRepository.delete` returns `null` (no avatar, or a concurrent delete already won the race), otherwise removes the file via `StorageService.delete`. `interfaces/avatar-response.interface.ts` — `AvatarResponse`/`toAvatarResponse`, serializing `UserAvatar.sizeBytes` (a Prisma `BigInt`) to a JSON-safe `string`, mirroring `RecordingResponse`.
- `src/auth/` — `AuthModule`, built with CQRS (`@nestjs/cqrs`); see [CQRS pattern](#cqrs-pattern) for the general convention it establishes:
  - `AuthController` (`POST /auth/register` → 201, `POST /auth/login` → 200, both returning `{ accessToken }`) depends only on `CommandBus`/`QueryBus`, not on a service.
  - `commands/register-user.command.ts` + `commands/handlers/register-user.handler.ts` — `RegisterUserCommand`/`RegisterUserHandler` (mutates state: dispatches `users`' `FindUserByEmailQuery` to check email uniqueness, hashes the password with `bcryptjs`, then dispatches `users`' `CreateUserCommand` to create the user). It never imports `UsersRepository` directly — the only coupling to `users/` is the shared `CreateUserCommand`/`FindUserByEmailQuery` message classes, dispatched via `CommandBus`/`QueryBus`.
  - `queries/login-user.query.ts` + `queries/handlers/login-user.handler.ts` — `LoginUserQuery`/`LoginUserHandler` (read-only: dispatches `users`' `FindUserByEmailQuery` to look up the user, verifies the password). Modeled as a query rather than a command because it doesn't mutate persisted state.
  - `token.service.ts` — `TokenService`, the shared JWT-signing provider (`@nestjs/jwt`, `JWT_SECRET`/1h expiry from `ConfigService`) used by both handlers.
  - `dto/` — `RegisterDto`/`LoginDto`, validated by `class-validator`.
  - `interfaces/access-token-response.interface.ts` — shared `{ accessToken: string }` response shape.
  - `interfaces/jwt-payload.interface.ts` — the decoded JWT shape, `{ sub: string; email: string }` (matches what `TokenService.sign` puts in the token).
  - `guards/jwt-auth.guard.ts` — `JwtAuthGuard`, a `CanActivate` guard that reads the `Authorization: Bearer <token>` header, verifies it via `JwtService.verifyAsync`, and attaches the decoded `JwtPayload` to `request.user`; throws `UnauthorizedException` (401) when the header is missing or the token is invalid/expired. Falls back to a `?token=` query param — the same token, verified the same way — only on routes decorated `@AllowQueryToken()` (`decorators/allow-query-token.decorator.ts`, read via `Reflector`), since a `<video>`/`<audio>` element's `src` can't set request headers; this is what lets `GET /meetings/:id/recordings/:recordingId/content` stay behind the guard while still being usable as a player `src`. Deliberately opt-in per route rather than a blanket fallback, so a token leaked via a recording URL (browser history, proxy logs, a `Referer` header) can't also authenticate the rest of the API.
  - `decorators/current-user.decorator.ts` — `@CurrentUser()` param decorator, reads `request.user` (set by `JwtAuthGuard`) and returns it typed as `JwtPayload`.
  - Register on a taken email throws `ConflictException` (409); bad login credentials throw `UnauthorizedException` (401).
  - `AuthModule` exports `JwtModule` and `JwtAuthGuard` so other feature modules can import `AuthModule` to protect their own routes with the same guard/decorator pair instead of re-registering `JwtModule`. It does **not** import `UsersModule` — `auth` and `users` are siblings under `AppModule`, communicating only through commands/queries dispatched on the shared `CommandBus`/`QueryBus`.
- `src/meetings/` — `MeetingsModule`, built with CQRS, importing `AuthModule` to reuse `JwtAuthGuard`/`@CurrentUser()`:
  - `MeetingsController`, guarded with `@UseGuards(JwtAuthGuard)` at the class level (`POST /meetings` → 201, `GET /meetings` → 200, `GET /meetings/:id` → 200/404, `GET /meetings/:id/recordings/:recordingId/content` → 200/206/404, `POST /meetings/:id/recordings` → 201, `DELETE /meetings/:id/recordings/:recordingId` → 204), every route reads the caller's id via `@CurrentUser()`.
  - `commands/create-meeting.command.ts` + `commands/handlers/create-meeting.handler.ts` — `CreateMeetingCommand`/`CreateMeetingHandler` (mutates state: creates a meeting owned by the current user).
  - `queries/get-meetings.query.ts` + `queries/handlers/get-meetings.handler.ts` — lists meetings owned by the current user; each item is a `MeetingListItemResponse` (`interfaces/meeting-list-item-response.interface.ts`) — the `Meeting` fields plus a `recordingCount: number` collapsed from the loaded recordings relation, for the list badge.
  - `queries/get-meeting-by-id.query.ts` + `queries/handlers/get-meeting-by-id.handler.ts` — looks up a single meeting scoped to `(id, ownerId)`; throws `NotFoundException` (404) both when the id doesn't exist and when it belongs to a different user, so ownership is never leaked via the status code. Also dispatches `meeting-summary/`'s `GetMeetingSummaryQuery` via the injected `QueryBus` (a cross-module read, not a direct repository import — see the CQRS pattern note below) to fetch the meeting's `MeetingSummary` row, if any. Returns a `MeetingDetailResponse` (`interfaces/meeting-detail-response.interface.ts`) — the `Meeting` fields plus a `recordings` field (every recording on the meeting, each serialized via `RecordingResponse`, ordered oldest-first) and a `summary` field (`MeetingSummaryResponse | null` via `meeting-summary/`'s `toMeetingSummaryResponse` — `null` when the meeting has no `MeetingSummary` row yet, e.g. no recording has reached `READY` transcription).
  - `queries/get-recording.query.ts` + `queries/handlers/get-recording.handler.ts` — `GetRecordingQuery`/`GetRecordingHandler`: takes `(meetingId, recordingId, ownerId, rangeHeader?)`; 404 for a missing/foreign meeting (via the lean `MeetingsRepository.findByIdAndOwner`) or a missing recording (via `RecordingsRepository.findById(meetingId, recordingId)`, itself scoped by both ids so a recording can't be streamed through a different meeting's URL); otherwise reads `MeetingRecording.sizeBytes`/`storagePath`/`mimeType` off that row, parses an optional `Range` header via `range-parser.ts`'s `parseRange` (single `bytes=start-end` ranges only — malformed or unsatisfiable ranges fall back to serving the whole file), and returns a `RecordingContent` (`interfaces/recording-content.interface.ts`: a `StorageService.createReadStream` `ReadStream` plus `mimeType`/`totalSize`/`range`) for `MeetingsController.getRecordingContent` to turn into the actual HTTP response — the handler stays HTTP-agnostic (no `Response`/header logic), consistent with the rest of this module's handlers.
  - `MeetingsController.getRecordingContent` (`GET /meetings/:id/recordings/:recordingId/content`, `@AllowQueryToken()`) sets `Content-Type`/`Accept-Ranges` from the `RecordingContent`, and either `Content-Length` (200, full file) or `Content-Range`/`Content-Length` plus a 206 status (when a satisfiable `Range` was parsed) via `@Res({ passthrough: true })`, then returns a `StreamableFile` wrapping the stream — Nest pipes it through without overwriting headers already set on `res`. The one route in this controller whose handler isn't a single `execute()` call (see the CQRS pattern note below) — the header/status logic is inherently HTTP-layer and can't move into an HTTP-agnostic query handler.
  - `meetings.repository.ts` — `MeetingsRepository` (thin Prisma wrapper: `create`, `findAllByOwner`, `findByIdAndOwner`, `findByIdAndOwnerWithRecordings`), declared directly in `MeetingsModule` (no other module currently needs it). `findByIdAndOwner` is a lean ownership/existence check (no join), used by the upload/delete/get-recording handlers, which never need the full recordings relation; `findAllByOwner`/`findByIdAndOwnerWithRecordings` both `include: { recordings: { orderBy: { createdAt: 'asc' } } }`, returning `MeetingWithRecordings` (`Meeting & { recordings: MeetingRecording[] }`) for the two callers that actually need it — `get-meetings` and `get-meeting-by-id` respectively — via the response-shaping functions `toMeetingListItemResponse`/`toMeetingDetailResponse`.
  - `recordings.repository.ts` — `RecordingsRepository` (thin Prisma wrapper: `create` — a plain insert, always giving the row a fresh permanent id — `findByMeetingId` (all of a meeting's recordings, oldest-first), `findById(meetingId, recordingId)` (scoped by both ids), `updateStatusIfCurrent(recordingId, data)`, `delete(meetingId, recordingId)`), declared directly in `MeetingsModule`.
  - `summary-reconciliation.service.ts` — `SummaryReconciliationService`, shared by `UploadRecordingHandler` and `DeleteRecordingHandler` (the two writes that can change what a meeting's summary should be based on): `reconcile(meetingId)` re-derives the meeting's summarization inputs fresh from `RecordingsRepository.findByMeetingId` — every `READY` recording's `id`/`transcriptText` as a `FoldableRecording` (already ordered by `createdAt`, `FAILED` ones excluded) plus whether every recording is now terminal — and calls `MeetingSummaryService.generateForMeeting` with them, fire-and-forget, logging (rather than throwing) any error. Runs for the same `meetingId` are chained one after another in an internal `Map<string, Promise<void>>` rather than fired concurrently: two recordings of the same meeting can finish (or be deleted) moments apart, each triggering `reconcile` independently, and `MeetingSummaryRepository`'s matched-on-current-row writes only guard against the meeting/row having been deleted mid-run — nothing stops a slower run (snapshotting an earlier, smaller set of recordings) from finishing after a faster one and overwriting its more complete result otherwise, which could wedge the summary at `PENDING` forever once every recording has actually gone terminal. Chaining means each run always re-reads the latest database state and there is never more than one in flight per meeting.
  - `dto/create-meeting.dto.ts` — `CreateMeetingDto` (`title`: non-empty string, `date`: ISO-8601 date string, `participants`: array of email strings), validated by `class-validator`.
  - No request-body DTOs beyond `CreateMeetingDto` — response shapes are the Prisma `Meeting`/`MeetingRecording` models (or the thin `MeetingListItemResponse`/`MeetingDetailResponse`/`RecordingResponse` wrappers above, for the fields those models can't represent directly — `recordingCount`, a nested `recordings` array, and `BigInt` serialization).
  - **Recording upload/delete:**
    - `MeetingsModule` imports `MulterModule.registerAsync({ inject: [ConfigService, StorageService], useFactory: ... })` (mirrors `AuthModule`'s `JwtModule.registerAsync` pattern) to build a `diskStorage` config from env at runtime: `destination` creates/uses `StorageService.resolveMeetingDir(meetingId)` (read from `req.params.id`), `filename` uses `StorageService.generateFilename(originalname)` — the same `{UPLOADS_DIR}/{meetingId}/{uuid}{ext}` convention `StorageService` documents, kept in one place instead of duplicated. `resolveMeetingDir` rejects any `meetingId` that isn't a plain UUID (400) — `:id` reaches it straight from the URL, before any ownership check runs, so without this a value like `..\..\Temp` would `path.join` outside `UPLOADS_DIR`. `limits.fileSize` reads `MAX_UPLOAD_SIZE_BYTES`; `fileFilter` validates both MIME type and extension against `ALLOWED_RECORDING_MIME_TYPES` (via `recording-file-filter.ts`'s `isAllowedRecordingFile`, allowlist parsed once at factory time by `parseAllowedMimeTypes`), rejecting with `UnsupportedMediaTypeException` (415) on mismatch. `assertKnownRecordingMimeTypes` runs once in the same factory and throws at bootstrap if `ALLOWED_RECORDING_MIME_TYPES` names a MIME type the extension map doesn't know — otherwise that misconfiguration would silently 415 every upload of it instead of failing loudly.
    - `MeetingsController.uploadRecording` (`@UseInterceptors(FileInterceptor('file'))`) throws `BadRequestException` (400) when `req.file` is `undefined` — multer doesn't error on a missing field, so this is the one case Nest's built-in Multer error mapping can't cover. Oversized (413) and malformed-multipart (400) requests are mapped automatically by Nest (`@nestjs/platform-express`'s `transformException`); no custom exception filter needed.
    - `commands/upload-recording.command.ts` + `commands/handlers/upload-recording.handler.ts` — `UploadRecordingCommand`/`UploadRecordingHandler`: checks meeting ownership via `MeetingsRepository.findByIdAndOwner` (404 for missing/foreign meetings — since the interceptor already wrote the file to disk before the handler runs, a 404 here also deletes that now-orphaned file via `StorageService.delete`), then `RecordingsRepository.create`s a new DB row for the file (a plain insert, not an upsert — every upload adds a recording rather than replacing one), then reads the meeting's authoritative current set via `RecordingsRepository.findByMeetingId` and calls `StorageService.pruneMeetingDir(meetingId, currentRecordings.map(r => r.storagePath))` to remove any file left in the meeting's directory that isn't one of those — based on the real directory listing taken _after_ the create commits (not a pre-write snapshot), so a losing concurrent upload's file is still cleaned up even though nothing ever read its metadata. Before returning the response, it also fires `transcribeInBackground(recording.id, recording.meetingId, recording.storagePath)` without awaiting it — background transcription must not add local-Whisper-inference latency to the upload's HTTP response. That private method: (1) writes `status: PROCESSING` via `RecordingsRepository.updateStatusIfCurrent(recordingId, ...)`; if that returns `false` (the recording has already been deleted) it returns immediately without calling Whisper at all; (2) otherwise calls `TranscriptionService.transcribe(storagePath)` and, on success, writes `status: READY` plus the returned `transcriptText` (again through `updateStatusIfCurrent`, so a completion racing a delete is silently dropped); (3) on a thrown error from transcription itself, writes `status: FAILED` the same guarded way and logs the error. Either way — `READY` or `FAILED` — it then calls the injected `SummaryReconciliationService.reconcile(meetingId)` (see above), the same fire-and-forget shape, injected directly the same way `TranscriptionService` is. It runs on both outcomes, not just `READY`, because a meeting's summary can only settle to its final status once every one of its recordings is terminal, and the terminal recording is not always the one that succeeds. The outer `.catch()` on `transcribeInBackground` only guards against a throw escaping the background call becoming an unhandled rejection — `SummaryReconciliationService` handles its own error logging.
    - `commands/delete-recording.command.ts` + `commands/handlers/delete-recording.handler.ts` — `DeleteRecordingCommand`/`DeleteRecordingHandler`: takes `(meetingId, recordingId, ownerId)`; 404 for a missing/foreign meeting; otherwise calls `RecordingsRepository.delete(meetingId, recordingId)`, which itself returns `null` (rather than throwing) if the row is already gone — e.g. a concurrent delete request won the race, or the id belongs to a different meeting — so that case also 404s instead of surfacing Prisma's `P2025` as an unhandled 500. Deletes the DB row before the file on disk (so a mid-failure never leaves a DB row pointing at a deleted file); deleting the row also deletes its `transcriptText`/`status`, since they're columns on that same row, not a separate table. Deleting one recording never touches its siblings — each row is independent. Before returning, it also fires `SummaryReconciliationService.reconcile(meetingId)` — unconditionally, regardless of the deleted recording's own status: it may have been (part of) the transcript a `READY` summary was built from, which must not linger once its source is gone, or it may have been the meeting's last non-terminal recording, whose removal now lets an otherwise-complete summary settle to `READY`.
    - `interfaces/recording-response.interface.ts` — `RecordingResponse`/`toRecordingResponse`: the one place `MeetingRecording.sizeBytes` (a Prisma `BigInt`) is serialized to a JSON-safe `string`, since `res.json()` throws on a raw `BigInt`. Consistent with the "no DTO layer, handlers return the model directly" convention — the model is just cloned with `sizeBytes` converted at the return boundary, not wrapped in a class. `status`/`transcriptText` pass through unchanged, so they're visible both on this upload response and nested under each entry of `MeetingDetailResponse.recordings` (`GET /meetings/:id`) — there is no separate route that returns recording metadata as JSON on its own; `GET /meetings/:id/recordings/:recordingId/content` streams one file's bytes, not its metadata.
- `src/transcription/` — `TranscriptionModule`, imported only by `MeetingsModule` (see above), the sole caller of `TranscriptionService`:
  - `transcription.service.ts` — `TranscriptionService`, HTTP-agnostic like `StorageService` (no Express types, no route, no `Response`): `transcribe(filePath)` runs the injected `WhisperRunner` against the file and pipes its raw stdout through `extractTranscriptText`, returning the plain transcript text (or rejecting, on a Whisper failure, for the caller to handle).
  - `whisper-runner.ts` — `WhisperRunner` (`(filePath: string) => Promise<string>`) and the `WHISPER_RUNNER` DI token it's injected under. Indirecting the actual Whisper call behind a token (rather than calling `nodejs-whisper` directly from the service) is what lets both unit tests and `meetings-recording.e2e-spec.ts` swap in a stub via `overrideProvider(WHISPER_RUNNER)`, so neither needs a working local Whisper install to run.
  - `transcription.module.ts` — provides `WHISPER_RUNNER` via a factory (`inject: [ConfigService]`) that wraps `nodejs-whisper`'s `nodewhisper(filePath, { modelName: 'base', autoDownloadModelName: 'base', modelRootPath: <WHISPER_MODEL_DIR>, removeWavFileAfterTranscription: true, whisperOptions: { splitOnWord: true, language: 'en' } })` — `'base'` is hardcoded (the PRD scopes out any other model size or making it configurable), `modelRootPath` is only set when `WHISPER_MODEL_DIR` is configured (unset lets `nodejs-whisper` fall back to its own default location). `language: 'en'` is hardcoded too, overriding `nodejs-whisper`'s default `-l auto`: the `base` model's language auto-detection is unreliable on accented/noisy audio and can mis-transcribe English speech as a different language entirely rather than just getting words wrong.
  - `transcript-text.ts` — `extractTranscriptText`, stripping whisper.cpp's per-segment `[00:00:00.000 --> 00:00:02.500]` timestamp prefixes from its raw stdout and joining the remaining text into one plain string (the PRD scopes out timestamps/diarization).
- `src/claude-agent/` — `ClaudeAgentModule`/`ClaudeAgentService`, a thin single-turn wrapper around `@anthropic-ai/claude-agent-sdk`, imported directly by `MeetingSummaryModule` (the only current caller):
  - `claude-agent.service.ts` — `ClaudeAgentService.ask(prompt, options)` delegates to the injected `ClaudeAgentRunner` and resolves with a `ClaudeAgentReply` (`{ text, structuredOutput }`). `options` (model, tools, permissionMode, cwd, mcpServers, ...) is forwarded to the SDK almost verbatim — there is no safe default applied, so a caller that omits `options.tools` gets the SDK's own default (the full built-in Claude Code toolset, including Bash and file access, running on this server's filesystem); a caller that wants a plain text/structured reply must pass `tools: []` itself.
  - `claude-agent-runner.ts` — `ClaudeAgentReply`: `text` is the SDK result message's plain-text `result` field; `structuredOutput` is that message's `structured_output` field, present only when the caller set `options.outputFormat`. Once `outputFormat` is set, `text` may be a placeholder rather than the actual answer (the turn ends on a tool_result carrier, with the real schema-validated output arriving as `structured_output`) — a caller using `outputFormat` must read `structuredOutput`, not `text` (see `MeetingSummaryService.summarize` below).
  - `claude-agent-runner.ts` — `ClaudeAgentRunner` (`(prompt: string, options: Options) => Promise<string>`) and the `CLAUDE_AGENT_RUNNER` DI token it's injected under, the same indirection shape as `WHISPER_RUNNER`/`WhisperRunner`, letting tests swap in a stub via `overrideProvider(CLAUDE_AGENT_RUNNER)` without a real SDK subprocess or network call.
  - `claude-agent.module.ts` — provides `CLAUDE_AGENT_RUNNER` via a closure that dynamically `import()`s `@anthropic-ai/claude-agent-sdk` (it's ESM-only; this app compiles to CommonJS, so a static import would fail) and drives its `query({ prompt, options })` async generator, returning the `result` field of the first `type: 'result'` message (throwing if that message's `subtype` isn't `'success'`, or if the generator ends without ever producing a `result` message). Authentication comes from `CLAUDE_CODE_OAUTH_TOKEN` in the process environment, inherited by the SDK subprocess whenever `options.env` is omitted. `options.abortController` is always replaced with a fresh `AbortController`, aborted by a `setTimeout(CLAUDE_AGENT_TIMEOUT_MS)` (3 minutes) started at the top of the call and cleared once the call settles — the SDK closes the subprocess's stdin and kills it if it doesn't exit on its own once that controller aborts. Whichever way the run then ends (an error thrown out of `query()`, or the generator ending without a `result` message), the `catch` checks `abortController.signal.aborted` and, if set, throws one clear "timed out" error instead of the generic message — this is what keeps a hung SDK subprocess from leaving `MeetingSummaryService.generateForMeeting` (and the meeting's `MeetingSummary.status`, and the web UI's spinner) stuck at `PROCESSING` forever.
- `src/meeting-summary/` — `MeetingSummaryModule`/`MeetingSummaryService`, generating a per-meeting summary/action items/decisions via `ClaudeAgentService`, incrementally across every one of a meeting's recordings as each reaches a terminal transcription status. Imported directly by `MeetingsModule`, the only current caller of `MeetingSummaryService` — mirrors `TranscriptionModule`'s direct-import/direct-service-injection shape for triggering a background job from another module's handler (see `UploadRecordingHandler` above). `MeetingSummaryModule` also imports `TasksModule` for `TaskService`, which `summarize` passes into `createMeetingToolsServer` (`../meeting-tools`) alongside `this`:
  - `meeting-summary.service.ts` — `MeetingSummaryService`: `summarize(meetingId, transcriptText, previous?)` calls `ClaudeAgentService.ask` with `buildSummaryPrompt(transcriptText, previous)` and `{ model: 'claude-haiku-4-5', tools: [], mcpServers: { meeting: await createMeetingToolsServer(meetingId, this.taskService, this) }, allowedTools: MEETING_ALLOWED_TOOLS, systemPrompt: MEETING_AGENT_SYSTEM_PROMPT, outputFormat: { type: 'json_schema', schema: SUMMARY_OUTPUT_JSON_SCHEMA } }` (Haiku is deliberately cheap/fast — this is a structured-extraction task, not open-ended reasoning, run as a background job on every recording that finishes transcribing). `tools: []` disables the SDK's built-in toolset; `allowedTools: MEETING_ALLOWED_TOOLS` then opens up exactly the three `meeting` MCP tools (`find_tasks`/`upsert_task`/`update_meeting`) and nothing else, so the agent can look up/record `Task` rows and write the meeting's summary itself as it works. `createMeetingToolsServer` is given `meetingId` directly — `summarize`'s own trusted parameter, not something read from the model's reply — so `upsert_task`/`update_meeting` always write against the meeting being summarized regardless of what the transcript says (see `meeting-tools.ts` below). `MEETING_AGENT_SYSTEM_PROMPT` instructs it to call `find_tasks` before ever creating a task (updating a similar existing one via `upsert_task` instead of duplicating it) and to ignore transcript remarks that aren't actually action items. `outputFormat`'s `SUMMARY_OUTPUT_JSON_SCHEMA` (`summary-response-parser.ts`, mirroring `SummaryGenerationResult`) makes the SDK itself enforce a valid shape on the final reply; since setting `outputFormat` can turn the SDK result's `text` into a placeholder (see `claude-agent-runner.ts` above), `summarize` reads `structuredOutput` when present and only falls back to `text` when it isn't. Either way, `parseSummaryReply` still runs on top as a second, defensive check tied to this app's exact contract (e.g. rejecting an empty `description`, which the JSON Schema alone doesn't), throwing a descriptive error (including a preview of the raw reply) on anything that doesn't parse as the expected JSON shape. On either kind of failure — the `ask()` call itself throwing (e.g. a transient SDK/API error) or `parseSummaryReply` rejecting the reply — `summarize` re-asks the agent with the same prompt/options up to `MAX_SUMMARY_ATTEMPTS` (3) times (the `ask()` call lives inside the per-attempt `try`, so both failure kinds are covered, not just parse failures) — logging each failed attempt via `Logger.warn` — before letting the last attempt's error propagate; a retried attempt is a brand-new agent conversation (no session resumed across attempts), so `update_meeting`'s overwrite is fine regardless, but `upsert_task`'s fuzzy title-similarity dedup could create a second `Task` if a retry phrases the same action item differently enough — a known, accepted gap, not a guarantee (see `apps/api/CLAUDE.md`'s Invariants). `summarize` also takes an optional 4th `meetingToolsServer` param — when a caller already built one (see `generateForMeeting` below), it's reused instead of `summarize` building an identical one itself. `generateForMeeting(meetingId, readyRecordings, allRecordingsTerminal)` is the background-job entry point `SummaryReconciliationService.reconcile` calls on every recording upload/delete that leaves the meeting's recordings changed, where `readyRecordings: FoldableRecording[]` is each `READY` recording's `{ id, transcriptText }`: when it's empty — e.g. every recording so far has failed transcription, none has finished yet, or the one recording that had reached `READY` was since deleted — it calls `MeetingSummaryRepository.deleteIfExists(meetingId)` and returns, so a meeting with no successfully transcribed recording never gets a summary row stuck in a processing state, and one that used to have a summary never keeps showing content whose source recording no longer exists. Otherwise it runs `findByMeetingId` (the meeting's current `MeetingSummary` row, if any) and `startProcessing` (writes `PROCESSING`, returning `null` if the meeting has since been deleted) concurrently via `Promise.all` — safe because `startProcessing` only ever touches `status`, never the fields `resumeFoldFrom` reads — then, once `started` confirms the meeting still exists, passes `existing` plus the new `readyRecordings`' ids to `resumeFoldFrom`, a module-level function that decides how much of the fold can be skipped: when `existing.foldedRecordingIds` is an exact, in-order prefix of the new id list (the common case — recordings finishing roughly in upload order), it returns a `startIndex`/`seed` pair that lets the fold resume from the already-persisted result and only process the new tail — including folding nothing at all (zero agent calls) when the id list hasn't changed, e.g. a run triggered by nothing but an unrelated recording's `FAILED` transition. An empty `foldedRecordingIds` is always treated as "nothing folded yet" (`startIndex: 0`, no seed) even when `existing.summaryText` is non-null — that combination means the content is a stale leftover from an `update_meeting` tool call mid-fold on a run that failed before ever setting `foldedRecordingIds`, and seeding a refold with it would be wrong. Otherwise (a recording finished out of order, or the ready set shrank because one was deleted) it returns `startIndex: 0`, forcing a full refold from scratch — the only way to stay correct in those cases. `generateForMeeting` then, if there's anything left to fold, builds one `meetingToolsServer` via `createMeetingToolsServer` and reuses it across every `summarize` call in the fold loop (rather than each call building its own), folds `readyRecordings.slice(startIndex)` through `summarize` in order starting from `seed` — each call's result becomes the next call's `previous` — and on success writes `summaryText`/`actionItems`/`decisions` from the final result plus the new `foldedRecordingIds` (the full new id list) via `updateStatusIfCurrent`, with `status: READY` when `allRecordingsTerminal` is `true` or `status: PENDING` when another recording is still transcribing (a later call, once it also reaches terminal, is what eventually flips it to `READY`); on any thrown error (including a `summarize` parse failure at any fold step), logs it and writes `FAILED` the same guarded way instead of a partial result — leaving `foldedRecordingIds` at whatever it was after the last successful run. This trailing `updateStatusIfCurrent` write stays the authority on final status/content — an agent run's own `update_meeting` tool call (see below) may transiently set `READY` mid-fold, but this write corrects it. `updateContent(meetingId, summaryText, decisions)` is a second, unrelated write path: it delegates straight to `MeetingSummaryRepository.upsertContent`, for a write that isn't derived from a transcript at all (and doesn't touch `foldedRecordingIds`) — this is what `meeting-tools.ts`'s `update_meeting` tool calls.
  - `meeting-summary.repository.ts` — `MeetingSummaryRepository` (thin Prisma wrapper, module-private — not exported, since only `MeetingSummaryService` and `meeting-summary/`'s own `GetMeetingSummaryHandler` touch it): `findByMeetingId`; a private `upsertOrNullIfMeetingDeleted(upsert)` helper runs a given `meetingSummary.upsert` call and swallows the FK-constraint (`P2003`)/not-found (`P2025`) error a since-deleted meeting produces, returning `null` instead of throwing — shared by `startProcessing`/`upsertContent` below so the swallowed-error-code list is only maintained once; `startProcessing(meetingId)` — `upsert`s the row to `PROCESSING`, creating it on the first run for a meeting, via that helper; `updateStatusIfCurrent(meetingId, data)` — `updateMany` matched on `meetingId` alone, the same matched-on-current-row approach `RecordingsRepository.updateStatusIfCurrent` uses (`data` may include `foldedRecordingIds`, see `generateForMeeting` above), returning `false` without writing anything once the meeting (and its cascaded summary row) is gone; `deleteIfExists(meetingId)` — `deleteMany` matched on `meetingId`, a no-op (not a throw) when there's no row, used by `generateForMeeting` when there's nothing left to summarize; `upsertContent(meetingId, { summaryText, decisions })` — `upsert`s `summaryText`/`decisions` directly and always settles the row at `READY`, creating it if the meeting doesn't have one yet (unlike `updateStatusIfCurrent`, which only ever updates an existing row), via that same `upsertOrNullIfMeetingDeleted` helper, used by `MeetingSummaryService.updateContent`, the entry point `meeting-tools.ts`'s `update_meeting` tool calls.
  - `summary-prompt.ts` — `buildSummaryPrompt(transcriptText, previous?)`, the prompt sent for meeting summarization. Tells the model to first use the `meeting` MCP tools (per `MEETING_AGENT_SYSTEM_PROMPT`) to record action items/write the summary, then submit a final answer with `summaryText` (string), `actionItems` (array of `{ description, assignee? }` — `assignee` included only when the transcript names a specific responsible person), and `decisions` (array of strings) — `options.outputFormat` (not this prompt) is what enforces that final shape via the SDK's structured-output mechanism. Deliberately never tells the model to answer with "only JSON, nothing else" — an earlier version did, and that phrasing made the model skip straight to a direct JSON answer without ever calling a `meeting` tool, silently defeating the whole `find_tasks`/`upsert_task`/`update_meeting` flow (see `apps/api/CLAUDE.md`'s Invariants). Also deliberately never mentions which meeting this is — the `meeting` MCP tools' `upsert_task`/`update_meeting` take no meeting id as input at all (see `meeting-tools.ts` below), so there's nothing for the model to echo back and no id in the prompt for a hostile transcript to try to override. When `previous` (a `SummaryGenerationResult`) is given, the prompt includes its `summaryText`/`actionItems`/`decisions` and instructs the model to extend and de-duplicate against it — the transcript is another recording of the same meeting, not an unrelated one — rather than restart from scratch.
  - `summary-response-parser.ts` — `parseSummaryReply(reply)`: strips a ` ```json ... ``` ` (or bare ` ``` ... ``` `) fence Claude sometimes wraps its reply in despite the prompt, `JSON.parse`s the rest, and validates every field's shape (including each `actionItems[]`/`decisions[]` entry), throwing a descriptive `Error` — the exact reason plus a truncated preview of the raw reply — on the first thing that doesn't match. Also exports `ActionItemPayload`/`SummaryGenerationResult`, the typed shape a successful parse produces.
  - `queries/get-meeting-summary.query.ts` + `queries/handlers/get-meeting-summary.handler.ts` — `GetMeetingSummaryQuery`/`GetMeetingSummaryHandler`: a read-only `MeetingSummaryRepository.findByMeetingId` lookup, dispatched cross-module by `meetings/`'s `GetMeetingByIdHandler` via `QueryBus` rather than a direct repository import (see the CQRS pattern note below).
  - `interfaces/meeting-summary-response.interface.ts` — `MeetingSummaryResponse`/`toMeetingSummaryResponse`: narrows a `MeetingSummary`'s JSON `actionItems`/`decisions` columns to their known `ActionItemPayload[]`/`string[]` shape (trusted because both columns are only ever written by `MeetingSummaryRepository` with data `MeetingSummaryService.summarize` produced), passes `foldedRecordingIds` straight through, and maps `null` through as `null` — consumed by `meetings/`'s `toMeetingDetailResponse`. `foldedRecordingIds` is exposed specifically so `apps/web`'s meeting detail page can tell a `READY` status that genuinely reflects every currently-`READY` recording apart from the transient `READY` `update_meeting`'s tool call can leave mid-fold (see `meeting-summary.service.ts`'s doc comment) — the mid-fold write never touches this column.
- `src/tasks/` — `TasksModule`/`TaskService`, a standalone `Task` model tracking action items independently of `MeetingSummary.actionItems`'s JSON blob. Not wired to any controller of its own — reached from `MeetingSummaryService.summarize`'s agent run via the `meeting` MCP tools (`find_tasks`/`upsert_task`, see `../meeting-tools`), from `find-tasks-server.ts`'s standalone process, and from `McpModule`'s `TaskTools` (`../mcp/task-tools.ts`):
  - `tasks.service.ts` — `TaskService`: `search(query, sourceMeetingId?)` delegates straight to `TaskRepository.search(query, undefined, sourceMeetingId)`. Left unset, `sourceMeetingId` keeps `search` meeting-agnostic (matches across every meeting's tasks) — this is what `find_tasks` (`../meeting-tools`) exposes as a read-only lookup, deliberately unscoped since that tool is only ever reached by this app's own trusted background job. Given, it restricts matches to that one meeting — this is what `../mcp/find-tasks-server.ts`'s standalone `find_tasks` tool uses instead, since that one is reachable by an external MCP client and must never search across every user's tasks (see `apps/api/CLAUDE.md`'s Invariants). `upsert({ title, sourceMeetingId, status? })` is a thin public entry point that chains its actual work (a private `doUpsert`) through `upsertQueues`, a `Map<string, Promise<unknown>>` keyed by `sourceMeetingId` — mirroring `SummaryReconciliationService.reconcile`'s per-`meetingId` chaining, except each call's own result/rejection is returned to its own caller rather than swallowed. This exists because the Claude Agent SDK can dispatch several tool calls from one model turn concurrently, and the search-then-write below isn't atomic: without the queue, two `upsert_task` calls for near-duplicate titles in the same meeting could both search before either write commits and both create a duplicate `Task`. `doUpsert` first calls `TaskRepository.search(title, 1, sourceMeetingId)` — scoped to that same meeting — to find the single best-matching existing task _belonging to that meeting_; if one clears the similarity threshold, it updates that row's `title`/`status` (passing `status: undefined` leaves the existing status untouched — Prisma's `update` ignores `undefined` fields) and returns it, otherwise it creates a new `Task` row. Scoping the dedup lookup to `sourceMeetingId` (unlike `search`) is deliberate: `upsert` is the write path an LLM agent tool (`upsert_task`) calls with a title drawn from a transcript, so an unscoped match could let a crafted or merely coincidental title in one meeting silently rewrite another meeting's task — with no meeting id involved in the attack at all. This is how the same action item mentioned more than once _within one meeting_ (e.g. across its own multiple recordings) collapses onto one row instead of piling up as duplicates; it deliberately does not collapse across different meetings. `findOpenTasks()` delegates to `TaskRepository.findByStatus(TaskStatus.OPEN)` (every `OPEN` task, most recently created first) and `findById(id)` to `TaskRepository.findById(id)` (`Task | null`) — both added for `McpModule`'s `tasks://open`/`task://{id}` resources (`../mcp/task-tools.ts`), no other caller yet.
  - `tasks.repository.ts` — `TaskRepository`, module-private (not exported — `TasksModule` exports `TaskService` only): `search(query, limit = 10, sourceMeetingId?)` runs a raw parameterized SQL query (`$queryRaw` with `Prisma.sql`) using Postgres `pg_trgm`'s `similarity("title", query)` — computed once per row in an inner subquery aliased `"titleSimilarity"`, then filtered/ordered by that alias in the outer query, rather than calling `similarity()` twice per row — filtering to a `MIN_TITLE_SIMILARITY` constant (`0.3`) and ordering most-similar-first — raw SQL is necessary here because Prisma's query builder has no `pg_trgm` support. `sourceMeetingId`, when given, adds a `WHERE "sourceMeetingId" = ...` clause inside that subquery, restricting matches to that one meeting's own tasks; `TaskService.upsert` passes it, `TaskService.search` (and therefore `find_tasks`) omits it. `create`/`update` are plain Prisma wrappers.
  - `TasksModule` exports `TaskService` directly (no controller, no CQRS command/query bus involved) — the same direct-injection shape `MeetingSummaryModule` uses for `MeetingSummaryService`, appropriate here too since nothing outside the backend reads `Task` data yet.
- `src/meeting-tools.ts` — a plain module (not a NestJS provider/service, no `@Injectable`) exposing `TaskService`/`MeetingSummaryService` as tools for a Claude Agent SDK run; wired into `MeetingSummaryService.summarize`'s `options.mcpServers`/`options.allowedTools` (see above). Typed against `TaskLookup`/`MeetingSummaryWriter` — structural subsets of `TaskService`/`MeetingSummaryService`, not the concrete classes — so this file has no import edge into `tasks/`/`meeting-summary/`; `MeetingSummaryService` importing `createMeetingToolsServer` from here while also being the `MeetingSummaryWriter` value passed into it would otherwise be a circular module import. `MEETING_TOOLS_SERVER_NAME` (`'meeting'`), `MEETING_TOOL_NAMES` (`['find_tasks', 'upsert_task', 'update_meeting']`) and `MEETING_ALLOWED_TOOLS` (the same three names qualified as `mcp__meeting__<tool>`, the form `Options.allowedTools` expects) are exported so a caller builds `options.mcpServers`'s key and `options.allowedTools` from the same source instead of re-typing the strings. `createMeetingTools(meetingId, taskService, meetingSummaryService)` builds three `tool()` definitions, scoped to `meetingId` — `find_tasks` (`{ query }`, `annotations: { readOnlyHint: true }`, delegates to `TaskService.search`; deliberately meeting-agnostic — since it's read-only, it can safely surface a similar task from a different meeting for the model's awareness, with no risk of that lookup itself mutating anything), `upsert_task` (`{ title, status? }` — no `sourceMeetingId` in the schema — delegates to `TaskService.upsert({ title, status, sourceMeetingId: meetingId })`, using the closed-over `meetingId`; note that even so, the create-vs-update decision inside `upsert` is _itself_ scoped to that same `sourceMeetingId` — see `tasks.service.ts` above — since binding `meetingId` at this layer alone wouldn't stop a title-similarity match from finding and updating a task that belongs to a different meeting), `update_meeting` (`{ summary, decisions }` — no `meetingId` in the schema — delegates to `MeetingSummaryService.updateContent(meetingId, summary, decisions)`, again the closed-over one, returning an `isError: true` `CallToolResult` when the meeting no longer exists) — each Zod-validated via the SDK's own `tool()` helper. Neither mutating tool accepts a meeting/task id as model input: `meetingId` comes from `summarize`'s own trusted parameter and is fixed at tool-creation time, so nothing the model reads from the transcript — including an attempt at prompt injection — can redirect a write to a different meeting. `createMeetingToolsServer` wraps that array in `createSdkMcpServer({ name: MEETING_TOOLS_SERVER_NAME, tools })`, producing the `McpSdkServerConfigWithInstance` a caller puts under `options.mcpServers.meeting`. `createMeetingTools` is exported separately (not inlined into `createMeetingToolsServer`) purely so its tools' `handler`s can be unit-tested directly, without going through the MCP server/transport layer. Both functions dynamically `import()` `@anthropic-ai/claude-agent-sdk` (it's ESM-only, same reason `claude-agent.module.ts` does) rather than a static import — this is why `test:e2e` needs `--experimental-vm-modules` too (see `apps/api/CLAUDE.md`'s Invariants).
- `src/mcp/find-tasks-server.ts` — a standalone task-manager MCP server exposing `find_tasks`/`upsert_task` tools and a `gather_meeting_info` prompt, unrelated to `meeting-tools.ts` above except that both end up calling `TaskService.search`/`upsert`: `meeting-tools.ts` builds an in-process SDK MCP server (`@anthropic-ai/claude-agent-sdk`'s `createSdkMcpServer`) consumed by `MeetingSummaryService`'s own agent run, while this file is a `node`-executable entry point an external MCP client spawns as its own subprocess and talks to over stdio, using the official `@modelcontextprotocol/sdk` (`McpServer`/`StdioServerTransport`) rather than the Claude Agent SDK — and unlike `meeting-tools.ts`, that package ships a CommonJS build, so the import here is a plain static one, no dynamic `import()` needed. Because an external MCP client (not just this app's own trusted background job) can spawn it, neither tool here can reuse `meeting-tools.ts`'s meeting-agnostic search or its "meetingId is closed over, never model input" write shape — there is no `meetingId` to close over ahead of time, and no per-transcript trust boundary to defend either; instead every call to either tool, and every `prompts/get` for the prompt below, must both name and be authorized against a `meetingId`, enforced the same way each time (see `apps/api/CLAUDE.md`'s Invariants):
  - `FindTasksContextModule` (`@Module`) is scoped to what `find_tasks`/`upsert_task`/`gather_meeting_info` need plus what that auth check needs — `ConfigModule.forRoot({ isGlobal: true })`, `JwtModule.registerAsync` (`inject: [ConfigService]`, `secret` from `JWT_SECRET` — verify-only, no `signOptions`, since nothing in this process issues tokens), `PrismaModule`, `TasksModule`, and `MeetingsRepository` registered directly as a provider (not by importing `MeetingsModule`, which would also drag in `TranscriptionModule`/`MeetingSummaryModule`/`AuthModule` and their Whisper/Claude Agent SDK dependencies this process has no use for) — booted via `NestFactory.createApplicationContext(FindTasksContextModule, { logger: false })` rather than the full `AppModule`; `logger: false` matters because this process's stdout carries nothing but the MCP protocol once `server.connect` attaches the transport, and Nest's own bootstrap logging would otherwise corrupt that stream.
  - `resolveUserId(config, jwtService)` runs once in `main()`, before `server.connect` ever attaches the transport: reads the `MCP_ACCESS_TOKEN` env var this process was spawned with (`config.getOrThrow`, so a missing var fails fast) — the same JWT `/auth/login` issues — and verifies it via `jwtService.verifyAsync<JwtPayload>(token)` (the same `JwtService`/`JWT_SECRET` `JwtAuthGuard` uses for every HTTP request), returning the payload's `sub` as `userId`. An invalid or expired token throws here and `main`'s `.catch` exits the process before any tool is even registered — there is no per-call bearer token; this server's entire stdio session speaks for whichever single user's token it was launched with, the same env-var-carries-a-secret shape this app already uses for `CLAUDE_CODE_OAUTH_TOKEN`.
  - `registerFindTasks(server, taskService, meetingsRepository, userId)` calls `server.registerTool('find_tasks', { description, inputSchema: { meetingId: z.string().uuid()..., query: z.string().min(1)... }, annotations: { readOnlyHint: true } }, handler)` — `inputSchema` is a Zod raw shape (not a `z.object(...)`), per the SDK's `registerTool` signature. The handler first calls `meetingsRepository.findByIdAndOwner(meetingId, userId)`; a `null` result (the meeting doesn't exist, or exists but belongs to someone else — indistinguishable on purpose, mirroring this app's "a foreign resource 404s, never 403s" rule) returns a generic `isError: true` `CallToolResult` (`Meeting ${meetingId} not found.`) without ever touching `TaskService`. Only once ownership is confirmed does it call `taskService.search(query, meetingId)` — the same method/implementation `meeting-tools.ts`'s `find_tasks` calls, just with the optional `sourceMeetingId` argument supplied this time, so both tools can never drift into different lookup behavior even though one is scoped and the other isn't.
  - `registerUpsertTask(server, taskService, meetingsRepository, userId)` mirrors `registerFindTasks`'s shape exactly, for the write path: `server.registerTool('upsert_task', { description, inputSchema: { meetingId: z.string().uuid()..., title: z.string().min(1), status: z.nativeEnum(TaskStatus).optional()... }, annotations: { readOnlyHint: false } }, handler)`. The handler runs the identical `meetingsRepository.findByIdAndOwner(meetingId, userId)` ownership check before touching `TaskService` at all, then calls `taskService.upsert({ title, status, sourceMeetingId: meetingId })` — the same `TaskService.upsert` method `meeting-tools.ts`'s `upsert_task` calls, just with `meetingId` supplied explicitly here rather than closed over at tool-creation time (there is no equivalent creation-time closure available to a standalone process an external client spawns). `TaskService.upsert`'s own dedup lookup already requires `sourceMeetingId` as part of its `UpsertTaskInput`, so unlike `search`, there was never a meeting-agnostic default to accidentally fall back to here.
  - `registerGatherMeetingInfoPrompt(server, meetingsRepository, userId)` calls `server.registerPrompt('gather_meeting_info', { title, description, argsSchema: { meetingId: z.string().uuid()... } }, handler)` — an MCP _prompt_ (`prompts/list`/`prompts/get`), not a tool: a reusable template a client offers a human to seed a conversation, rather than something an agent calls mid-task. The handler runs the same `meetingsRepository.findByIdAndOwner(meetingId, userId)` check as the two tools, but a failed check `throw`s a plain `Error` instead of returning an `isError: true` result — `GetPromptResult` (the `prompts/get` response shape) carries `description`/`messages` only, no error field of its own, so the SDK's request handler has no way to surface a failure except as a thrown JSON-RPC error; the message text is still the same generic "not found" string the two tools use, for the same reason. Once ownership is confirmed, it returns one `user`-role text message built from `meeting.title`/`meeting.date.toISOString()`/`meeting.participants` (joined, or `'none recorded'` when empty) plus the `meetingId` itself, instructing the assistant to interview the caller about what was discussed/decided and to call `find_tasks` before `upsert_task` — both scoped to that same `meetingId` — so the two tools and the prompt stay consistent about which meeting is in play.
  - `main()` also installs `SIGINT`/`SIGTERM` handlers that close the Nest context before exiting. Built by the normal `nest build` (`tsc` compiles every file under `src`, this one included) to `dist/src/mcp/find-tasks-server.js`; `mcp:find-tasks` runs that built file, `mcp:find-tasks:dev` runs the `.ts` source directly via `ts-node` (see `apps/api/CLAUDE.md`'s Commands) — both need `DATABASE_URL`, `JWT_SECRET`, and `MCP_ACCESS_TOKEN` set in the environment.
  - `TaskService.search(query, sourceMeetingId?)` (`tasks/tasks.service.ts`) grew this second, optional parameter for exactly this caller — it passes straight through to `TaskRepository.search(query, undefined, sourceMeetingId)`, the same repository method/signature `TaskService.upsert`'s dedup lookup already uses to scope to one meeting (see `tasks.service.ts` above). Left unset, behavior is unchanged: `meeting-tools.ts`'s `find_tasks` still gets `TaskService`'s original meeting-agnostic search.
- `src/mcp/mcp.module.ts`/`mcp.service.ts`/`mcp.controller.ts`/`task-tools.ts` — `McpModule`, a second, unrelated MCP surface from `find-tasks-server.ts` above: an in-process HTTP endpoint (`POST/GET/DELETE /mcp` via `McpController`'s single `@All()` handler) rather than a spawned stdio subprocess. `McpService.createTransport()` builds a **fresh** `McpServer({ name: 'video-meetings', version: '1.0.0' })` and `StreamableHTTPServerTransport({ sessionIdGenerator: undefined, enableJsonResponse: true })` on **every call**, calls `taskTools.registerOn(server)`, then `server.connect(transport)`, and returns the transport — never a single shared instance, since the SDK's stateless transport (`sessionIdGenerator: undefined`) throws on a second `handleRequest` call and `McpServer.connect` refuses a second `connect()` without an intervening `close()` (see `apps/api/CLAUDE.md`'s Invariants for how this was found). `McpController`'s handler calls `createTransport()`, registers `res.on('close', () => transport.close())` for cleanup, then forwards `(req, res, req.body)` into `transport.handleRequest` — `@Res({ passthrough: false })` because the SDK writes the response itself. `sessionIdGenerator: undefined` puts each transport in stateless mode (no `Mcp-Session-Id` handshake); `enableJsonResponse: true` makes it reply with a plain JSON body instead of opening an SSE stream. Not authenticated yet — every route on this controller, and everything `TaskTools` registers, is reachable by any caller.
  - `task-tools.ts`'s `TaskTools` (`@Injectable`, `TaskService` injected via DI) is what `registerOn(server)` registers: the `find_tasks`/`upsert_task` tools plus `tasks://open`/`task://{id}` resources, each delegating straight to a `TaskService` method — `search`, `upsert`, `findOpenTasks`, `findById` — with no dedup/search/write logic reimplemented here, only translated into the MCP tool/resource call shape. Unlike `meeting-tools.ts` (a plain module building Claude Agent SDK tools, no `@Injectable`, `meetingId` closed over at creation time) and `find-tasks-server.ts` (a standalone process resolving `TaskService` from its own narrow `NestFactory.createApplicationContext`), this one runs inside the main app's DI container. `find_tasks`'s `meetingId` argument is optional, mirroring `TaskService.search`'s own optional `sourceMeetingId` — omitted, it searches across every meeting's tasks, same as `meeting-tools.ts`'s in-process `find_tasks`. `upsert_task`'s `meetingId` is required, mirroring `UpsertTaskInput.sourceMeetingId` (no optional form) — there's no per-run meeting id to close over the way `meeting-tools.ts` does, so the caller supplies it explicitly, the same shape `find-tasks-server.ts`'s standalone `upsert_task` uses. `tasks-open` is a plain (non-templated) resource at the fixed URI `tasks://open`, returning every `OPEN` task as a JSON array via `TaskService.findOpenTasks()`. `task` is a `ResourceTemplate('task://{id}', { list: undefined })` — `list: undefined` because there's no meaningful way to enumerate every task id as a resource list — whose read callback calls `TaskService.findById(id)` and throws a plain `Error` (`Task ${id} not found.`) when it's `null`; like `gather_meeting_info`'s ownership-check failure in `find-tasks-server.ts`, `ReadResourceResult` has no error field of its own, so a thrown `Error` is the only way to surface a failure to the client. None of this is authorization-gated (see `apps/api/CLAUDE.md`'s Invariants).

## CQRS pattern

Every feature module that mutates or reads persisted state follows the `@nestjs/cqrs` convention established by `auth/` (see above) and reused by later modules (e.g. `meetings/`). New feature modules should follow the same shape rather than inventing a new one:

- **Commands** (`commands/<name>.command.ts` + `commands/handlers/<name>.handler.ts`) are for anything that mutates state (create/update/delete). The command class is a plain constructor-only data carrier with no logic. Its handler is decorated `@CommandHandler(XCommand)` and implements `ICommandHandler<XCommand, TResult>`.
- **Queries** (`queries/<name>.query.ts` + `queries/handlers/<name>.handler.ts`) are for anything read-only — including reads that do non-trivial work, as long as they don't persist anything. `LoginUserQuery` is the reference example: it looks up a user and verifies a password hash, but is a query (not a command) because nothing is written to the database.
- **Controllers stay thin.** They inject `CommandBus`/`QueryBus` only — never a repository or a handler directly — and each route handler is a single `commandBus.execute(new XCommand(...))` or `queryBus.execute(new XQuery(...))` call, typed to return the handler's result. The sanctioned exception is a streaming response (`MeetingsController.getRecordingContent`): the `execute()` call still does all the business logic, but the controller also translates its result into response headers/status via `@Res({ passthrough: true })`, since that's inherently HTTP-layer work an HTTP-agnostic handler can't do.
- **Handlers hold the logic.** They inject one or more thin repositories (one per aggregate, e.g. `UsersRepository`, `MeetingsRepository` — each a near-1:1 wrapper around a `PrismaService` call, returning the Prisma model type directly) plus any shared services (e.g. `TokenService`). Handlers throw Nest's built-in HTTP exceptions directly where a business rule is violated (`ConflictException`, `UnauthorizedException`, `NotFoundException`, …) — there is no separate exception-mapping layer.
- **Module wiring:** each feature module imports `CqrsModule`, declares local `CommandHandlers`/`QueryHandlers` arrays, and registers `providers: [...CommandHandlers, ...QueryHandlers]` alongside its controller and any module-local services. `@nestjs/cqrs`'s explorer scans the whole application for `@CommandHandler`/`@QueryHandler` providers regardless of which module declared `CqrsModule`, so `CommandBus`/`QueryBus` dispatch works across module boundaries as long as every feature module is reachable from `AppModule`.
- **Cross-module communication goes through the bus, not direct imports.** `MeetingsRepository` is declared directly in `MeetingsModule` (no other module currently needs it) — that's the simple case. But `users/` is a dependency of `auth/`, and that dependency is expressed as commands/queries (`CreateUserCommand`, `FindUserByEmailQuery`), not as an exported repository: `UsersRepository` is a module-private provider, `auth/` handlers only import the `users/` command/query _classes_ (plain data carriers) and dispatch them via `CommandBus`/`QueryBus`. This keeps `AuthModule` from importing `UsersModule` at all — both are imported side-by-side by `AppModule`. Reach for this pattern (bus-mediated command/query, no cross-module repository export) whenever a new feature module needs another module's persisted data; keep the direct-declaration pattern (`MeetingsRepository`'s) only for a repository nothing outside its own module touches.
- **DTOs vs commands/queries:** HTTP-facing validation lives in `dto/*.ts` (`class-validator` decorators); controllers map a validated DTO onto a command/query instance. Commands/queries themselves carry no validation logic — by the time a handler sees one, the shape is already trusted.

## Database (Prisma)

- Schema: `prisma/schema.prisma` — `User` (mapped to `users`), `Meeting` (mapped to `meetings`, `ownerId` FK to `User` with `onDelete: Cascade`, `participants` stored as a native Postgres `String[]` column rather than a separate join table, `recordings: MeetingRecording[]`, `summary: MeetingSummary?`, `tasks: Task[]`), `MeetingRecording` (mapped to `meeting_recordings`, `meetingId` FK to `Meeting` with `onDelete: Cascade` — no `@unique` on `meetingId`, so a meeting can hold any number of recordings — `originalFilename`, `storagePath`, `mimeType`, `sizeBytes` as `BigInt`, `status` as the `RecordingStatus` enum (`UPLOADED | PROCESSING | READY | FAILED`, default `UPLOADED`), `transcriptText` as a nullable `String` — populated only once that recording's own background transcription reaches `READY`, and deleted along with the rest of the row by `RecordingsRepository.delete`/the FK cascade, since it's a column on `MeetingRecording` rather than a separate table), `MeetingSummary` (mapped to `meeting_summaries`, `meetingId` FK to `Meeting` with `onDelete: Cascade` and `@unique` — one summary row per meeting, covering every one of its recordings — `status` as the `SummaryStatus` enum (`PENDING | PROCESSING | READY | FAILED`, default `PENDING`, mirroring `RecordingStatus`'s shape), `summaryText` as a nullable `String`, `actionItems`/`decisions` as `Json` columns (each defaulting to `"[]"`) holding the structured shape `meeting-summary/summary-response-parser.ts`'s `ActionItemPayload[]`/`string[]` describe — always written by `MeetingSummaryRepository` with data `MeetingSummaryService` produced, never from untrusted input — and `foldedRecordingIds` as a native Postgres `String[]` column (default `[]`) recording which `MeetingRecording` ids, in order, are already reflected in `summaryText`/`actionItems`/`decisions`, so `MeetingSummaryService.generateForMeeting` can resume folding from the first not-yet-included recording instead of always refolding every ready recording from scratch — see that method's bullet above), `Task` (mapped to `tasks`, `sourceMeetingId` FK to `Meeting` with `onDelete: Cascade`, `title` as a plain `String`, `status` as the `TaskStatus` enum (`OPEN | IN_PROGRESS | DONE`, default `OPEN`) — no assignee field, deliberately: there is no concept of a responsible user yet — plus a `@@index` of `type: Gin` on `title` with the `gin_trgm_ops` operator class, backing `TasksRepository.search`'s Postgres `pg_trgm` similarity lookup; the `pg_trgm` extension itself is enabled by the `add_task` migration via `CREATE EXTENSION IF NOT EXISTS pg_trgm`, not declared in `schema.prisma`), and `UserAvatar` (mapped to `user_avatars`, `userId` FK to `User` with `onDelete: Cascade` and `@unique` — a user has at most one avatar — `originalFilename`, `storagePath`, `mimeType`, `sizeBytes` as `BigInt`, mirroring `MeetingRecording`'s shape, minus the transcription fields). Migrations live in `prisma/migrations/`.
- CLI config: `prisma.config.ts` (reads `DATABASE_URL` via `dotenv/config`) — used by `prisma migrate`/`prisma generate`, separate from the app's own `ConfigModule`-based runtime connection in `PrismaService`.
- Generated client: `generated/prisma`-style output is not used here — the schema uses the classic `prisma-client-js` generator, so the client is generated into `node_modules/@prisma/client` and imported as `import { PrismaClient } from '@prisma/client'`.
- Required env vars (`apps/api/.env`, see `.env.example`): `DATABASE_URL` (Postgres connection string — must match the credentials in the root `docker-compose.yml`/`​.env.example`) and `JWT_SECRET`. `PORT` (default `3001` in `.env`/`.env.example`) sets the HTTP listen port in `src/main.ts` — it must differ from `apps/web`'s port (3000) since both apps are run together via `pnpm dev`. `WEB_URL` (default `http://localhost:3000`) sets the allowed CORS origin in `src/main.ts` — it must match wherever `apps/web` is actually served from. `UPLOADS_DIR` (default `uploads`, relative to `apps/api/`) is where `StorageService` writes recording files — gitignored/dockerignored, created on demand. `MAX_UPLOAD_SIZE_BYTES` and `ALLOWED_RECORDING_MIME_TYPES` (comma-separated MIME list, includes `audio/mpeg` alongside the video types) enforce the upload route's size/type validation via `MeetingsModule`'s `MulterModule.registerAsync` config (`StorageService` itself doesn't check them — see the recording upload/delete bullet below). `MAX_AVATAR_SIZE_BYTES` and `ALLOWED_AVATAR_MIME_TYPES` are the same pair for the avatar upload route, enforced via `UsersModule`'s `MulterModule.registerAsync` config — see the avatar upload/delete bullet above. `WHISPER_MODEL_DIR` (optional) sets `modelRootPath` for `nodejs-whisper`'s local Whisper `base` model — see the `src/transcription/` bullet above; left unset, `nodejs-whisper` falls back to its own default download location.
